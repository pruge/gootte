# T03 — 프론트 쿼리 캐시 다이어트

**Blocked by:** 없음 — 즉시 착수 가능

## Goal

켜둔 탭의 쿼리 캐시 상주량을 줄인다: 보관 기한 단축, 포커스 refetch 중단, 영속 저장 범위 축소(S1).

## Why this slice

유휴 메모리 증가의 가장 큰 프론트 원인이 여기다 — 24시간 GC 유예 + 포커스마다 refetch + 변경마다 전량 직렬화. 세 손잡이가 한 파일(`query.ts`)에 모여 있어 한 슬라이스로 묶는다.

## Produces

- 짧은 `gcTime`·`refetchOnWindowFocus: false`·좁아진 영속 저장. 화면이 보여주는 값은 WS invalidate 가 메우므로 동일하다.

## Consumers

- 전 탭(`features`·`plan`·`process`·`memo`) — 쿼리 키는 그대로, 보관만 짧아진다.
- `useLiveSync` — invalidate 신호가 최신값 공급자로 남는다(T04 와 함께 확인).
- `hydrateFromStorage` — 저장본 형식은 그대로, 범위가 좁아진다.

## Touched surfaces

- `code/web/frontend/src/lib/query.ts` — `PERSIST_GC`·`defaultOptions`·`attachSaver`·`shouldDehydrateQuery`.

## Explicitly out of scope

- invalidate 범위 변경(T04). live.ts 금지.
- 영속 키 이름 변경·마이그레이션 — 키 유지, 자연 교체(D-데이터 절).
- `featureDoc` 메모리 보관 — 필요하면 후속으로, 여기선 손대지 않는다.

## Locked decisions

- D2(INV-1) — 캐시를 좁혀도 파생 경로를 새로 만들지 않는다. 서버 재계산값을 그대로 쓴다.
- D3(INV-3) — stale 폭은 WS invalidate 가 메운다. 폴백 폴링 환경에서도 15초 상한은 유지된다.

## Evidence anchors

- `makeQueryClient` 의 `staleTime`·`gcTime`·`refetchOnWindowFocus`.
- `attachSaver` 의 500ms 디바운스 + 전량 `JSON.stringify`.
- `shouldDehydrateQuery` 의 `featureDoc` 제외 조건(확장 지점).

## Regression guards

- `frontend/test/app.test.tsx` 및 query 관련 프론트 테스트.
- 새로고침 후 즉시 그리기(T07 의도) 회귀 — 영속본이 좁아져도 첫 프레임 빈 화면 금지.

## Scope

- `query.ts` 한 파일 + 프론트 테스트. 그 외 금지.

## Implementation notes

- `gcTime` 24h → 10분, `refetchOnWindowFocus: false` 가 출발점. 수치는 실측 후 Comments 에 기록한다.
- 영속은 현재 프로젝트의 `features`·`plan` 위주로 좁히고, 저장 디바운스를 수 초로 늦춘다.

## Acceptance criteria

- 같은 시나리오에서 웹뷰 프로세스 상주가 감소한다(A1).
- 새로고침 직후 이전처럼 읽은 내용이 바로 그려진다(빈 화면 없음).
- `pnpm verify` green(A5).

## Verification

- `pnpm verify` + 변경 전후 RSS 비교(동일 시나리오 30분 방치).
