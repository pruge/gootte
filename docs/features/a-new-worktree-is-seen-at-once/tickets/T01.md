# T01 — 워크트리가 생기면 감시를 다시 묶는다

**Blocked by:** 없음 — 즉시 착수 가능

**Time:** started=2026-09-04T16:27:26+09:00 finished=2026-09-04T16:42:08+09:00

## Goal

**워크트리 컨테이너를 얕게 감시하고, 슬롯이 생기거나 사라지면 콘텐츠·커밋 감시를 재바인딩한다.**
그래서 새 워크트리 안의 `gootte start` 가 **다른 사본과 똑같이 push 로 나간다.**

## Why this slice

한 장이면 끝난다. 고칠 자리가 `watch.ts` 하나이고, 읽기 경로는 이미 맞기 때문이다
(`readFeatures`·`scanWorkingCopies` 가 워크트리를 이미 합집합으로 본다).
**신호만 붙이면 되는 일**을 여러 장으로 쪼개면 오히려 경계가 흐려진다.

## Produces

- `watch.ts` 에 워크트리 컨테이너 감시 + 재바인딩 경로
- 그것을 고정하는 테스트(새 워크트리를 만들고 그 안의 편집이 `{project}` 를 쏘는지)

## Consumers

`backend/src/watchers.ts` → `server.ts` 의 WS push → 프론트 재조회.
**소비처 코드는 안 바뀐다** — 같은 `Change` 신호가 더 자주 나갈 뿐이다.

## Touched surfaces

- `code/web/core-io/src/watch.ts` — 감시 경로와 재바인딩
- `code/web/core-io/src/treehouse.ts` — 컨테이너 뿌리를 내주는 함수가 필요하면 여기(이미
  `defaultBbWorktreeRoot`·`bbWorktreeRoots`·`extraWorktreeRoots` 가 산다)
- `code/web/core-io/src/watch.test.ts` — 회귀 고정

## Explicitly out of scope

- `discoverProjects` 의 판정 — 워크트리는 **프로젝트가 아니라 사본**이다. 목록에 넣지 않는다.
- 15초 폴러 · `watch-fallback` 경로.
- 프론트엔드 · 백엔드 라우트.

## Locked decisions

- **`rediscover` 를 고치지 않고 별도 재바인딩 경로를 둔다.** `rediscover` 의 조기 반환
  (`if (!changed) return;`)은 **프로젝트 목록**에 대한 올바른 최적화다. 사본 목록은 그것과
  다른 축이므로 같은 함수에 얹으면 둘 다 흐려진다.
- **얕게만 본다.** 컨테이너 아래로 재귀하지 않는다 — 슬롯이 *생겼다*는 것만 보면 되고,
  그 안의 문서는 재바인딩된 콘텐츠 감시가 본다.
- 🔴 **`NEVER`(`.codegraph`)를 계속 존중한다.** 소켓에 `fs.watch` 를 걸어 백엔드를 통째로
  내린 전례가 있다(`watch.ts:14-19`).
- **슬롯이 사라지는 것도 재바인딩 사건이다** — 안 그러면 죽은 경로를 계속 붙들고 있게 된다.

## Evidence anchors

- `core-io/src/watch.ts:88` — `copyPathsOf` 가 바인딩 시점에 한 번 계산된다.
- `core-io/src/watch.ts:225-250` — `rediscover` 와 `listWorthy`(왜 두 워크트리가 안 걸리는지).
- `backend/src/snapshot-revalidator.ts:5` · `frontend/src/lib/live.ts:24` — 15초는 fallback 전용.
- `frontend/src/lib/query.ts:31` — 지금 유일하게 구해 주는 길(창 포커스).
- `core-io/src/treehouse.ts` — 워크트리 두 종류의 경로 규칙 SoT.

## Regression guards

- **기존 감시가 그대로 돈다** — `watch.test.ts` 의 기존 케이스가 전부 통과해야 한다.
- 🔴 **감시 실패가 서버를 죽이지 않는다** — 새로 거는 감시에도 `onWatchError` 를 붙인다.
  듣는 사람 없는 `error` 이벤트는 uncaught 로 다시 던져진다(`watch.ts:143-152`).
- **INV-2** — 관측 후 워크트리 워킹트리가 깨끗한지 테스트가 확인한다(기존 `scanWorkingCopies`
  테스트가 같은 것을 지킨다).

## Scope

1. 워크트리 **컨테이너 뿌리**를 내주는 함수를 정한다 — BB 는 `GOOTTE_BB_WORKTREES`(기본
   `~/.bb/worktrees`), Claude 는 각 사본의 `.claude/worktrees`.
   🔴 없는 디렉토리를 거는 것이 오류가 되지 않게 한다(아직 안 생겼을 수 있다).
2. 그 뿌리를 얕게 감시한다. 슬롯 추가/삭제 이벤트 → debounce → 재바인딩.
3. 재바인딩 = `contentPaths`·`gitRefPaths` 를 다시 계산해 **차분만** `add`/`unwatch` 한다.
   목록이 그대로면 아무것도 안 한다(조용한 no-op).
4. 재바인딩 뒤 그 프로젝트에 `{project}` 를 한 번 쏜다 — 새 워크트리가 이미 갖고 있던
   내용이 화면에 반영되어야 한다(생기자마자 티켓이 들어 있는 경우).
5. 테스트: 임시 디렉토리에 프로젝트 + BB 컨테이너를 합성 → 감시 시작 → **그 뒤에** 워크트리를
   만들고 티켓을 편집 → `{project}` 가 오는지. Claude 워크트리로도 같은 것 한 번.

## Implementation notes

- 컨테이너가 나중에 생기는 경우가 있다(`~/.bb/worktrees` 자체가 없다가 첫 스레드에 생김).
  chokidar 는 없는 경로도 받아 두지만 **정말 그런지 테스트로 확인하고**, 아니면 부모를 건다.
- 슬롯 이름은 BB `<env_XXXX>/<프로젝트>`, Claude `<이름>` 으로 **깊이가 다르다**
  (`treehouse.ts` 가 SoT). 두 규칙을 한 함수에 뭉개지 말고 각자 그대로 둔다.
- debounce 는 기존 `debounceMs`(150ms)를 그대로 쓴다 — 워크트리 생성은 파일 여럿을 한꺼번에
  만든다.

## Acceptance criteria

- AC1 — 감시 시작 **뒤에** 생긴 BB 워크트리 안의 티켓 편집이 `{project}` 를 쏜다.
- AC2 — 같은 것이 Claude Code 워크트리(`<프로젝트>/.claude/worktrees/<이름>`)에서도 된다.
- AC3 — 워크트리가 **사라지면** 그 경로가 감시에서 빠진다.
- AC4 — 기존 `watch.test.ts` 케이스가 전부 그대로 통과한다(회귀 없음).
- AC5 — 새 감시가 실패해도 서버가 죽지 않고 `onError` 로 통보된다.
- AC6 — `pnpm verify` green.
- AC7 — 🔴 **화면에서 실제로 확인한다** — 격리 포트로 dev 서버를 띄우고(스킬
  `gootte-dev-server`), 창 포커스를 **주지 않은 채로** 새 워크트리의 편집이 반영되는지 본다.
  창을 떠났다 오면 어차피 보이므로, **떠나지 않고 보이는 것**이 이 기능의 전부다.

### 2026-09-04 — 구현 기록

**AC7(화면 확인)은 통과했고, 증거를 남겨 둔다.** 합성 프로젝트(임시 뿌리 + 임시 BB 뿌리, 격리
포트 8899/5399)로 띄우고 **감시가 도는 중에** BB 워크트리를 만들어 그 안의 티켓에 `started=` 를
넣었다. 화면의 `처리중` 이 **0 → 1** 로 바뀌었고, 같은 순간 페이지의 `focus` 이벤트 0회 ·
`visibilitychange` 0회였다(`document.hasFocus()` 는 내내 `true`). 🔴 **포커스가 아니라 push 로 온
것이 이 두 숫자로 증명된다** — 이 티켓이 고치려던 것이 정확히 그것이다.
실제 `~/.bb` 와 캡틴 저장소는 건드리지 않았다(`git worktree list` 로 확인).

**AC3 은 통과하지만 내 코드가 준 것이 아니다.** "워크트리가 사라지면 감시에서 빠진다" 는
구현을 되돌리고 돌려도 통과한다 — 지워진 디렉토리의 감시는 chokidar 가 OS 수준에서 이미 놓는다.
`rebindCopies` 의 `unwatch` 는 **관측되는 동작이 아니라 장부 정리**다. 그래서 그 테스트는
회귀 가드가 아니라 **성질 기록**으로 이름과 주석을 바꿔 두었다. 나머지 두 테스트(AC1·AC2)는
구현을 되돌리면 실제로 실패하는 것을 확인했다 — 그 둘이 진짜 가드다.

**컨테이너를 못 잡는 경우가 하나 남는다.** 컨테이너에서 위로 두 칸 안에 존재하는 디렉토리가
없으면 그 종류는 이번 실행에서 못 잡는다(예: BB 를 한 번도 안 쓴 기계에는 `~/.bb` 조차 없다).
🔴 홈 디렉토리를 통째로 거는 것보다 못 잡는 편이 낫다고 판단했다. 그 경우는 재시작 때 잡힌다.
