# firstmate-project-source — 관리 대상을 firstmate 프로젝트로 전환

Status: ready-for-agent (2026-08-09) · 열린 결정 전부 캡틴이 닫음 (§결정) · 티켓 4장 `issues/` 에 있음

자매 사양 [`../firstmate-migration/spec.md`](../firstmate-migration/spec.md) 은 **저장소**를 정리한다.
이 사양은 **제품이 무엇을 읽는가**를 바꾼다. 둘의 순서 요구는 자매 사양 §순서.

## 캡틴 지시 (원문)

> 기능을 새로 계획할꺼야. ai2/projects의 관리하게 전환, features 바라보게 수정.
> issues 처리할일 목록, ~/.treehouse에서 처리중인 목록을 확인하여 처리중으로 처리.

## 문제

gootte 는 cling 프로젝트를 실시간으로 관리한다 — 프로젝트 문서를 읽어 "지금 무엇이 참인가 · 다음은 무엇인가"를
칸반·타임라인·digest 로 보여준다. 그런데 캡틴의 프로젝트들은 firstmate 관리로 옮겨갔고, cling 워크플로우는
은퇴했다. 지금 규칙대로면 gootte 는 **관리 대상을 하나도 찾지 못한다** — 발견 조건이 `.cling/profile.md`
존재이기 때문이다(F1).

읽을 자리는 이미 다 있다. firstmate 프로젝트는 기능별로 사양과 티켓을 파일로 갖고 있고(F3),
지금 누가 무엇을 붙들고 있는지는 격리 사본이 그대로 말해준다(F6·F7). gootte 가 볼 곳만 바꾸면 된다.

## 불변식

이 프로젝트의 기존 불변식이 그대로 이 기능을 규정한다. 새로 만들지 않는다.

- **INV-1 — 파생물만 만든다.** 처리중 여부·할일 목록은 전부 원본에서 재계산되는 값이다.
  손으로 유지되는 두 번째 SoT 를 만들지 않는다.
- **INV-2 — 관리대상은 읽기 전용.** `docs/features/` 아래 어떤 파일도 gootte 가 고치지 않는다.
  쓰기는 자기 `.gootte/` 네임스페이스에만.
- **INV-3 — 뷰는 항상 현재 SoT 를 반영한다.** stale 뷰 금지.
- **INV-4 — read-path 는 결정적이고 LLM 을 쓰지 않는다.** 아래 매핑 규칙이 전부 규칙 기반이어야 하는 이유다.
  이름이 비슷하니 아마 이 티켓일 것이다 식의 추정은 이 불변식 위반이다.

## 설계 — 세 가지 판정

> **구현 지형도는 [`architecture.md`](architecture.md).** 티켓 01 이 남긴 구조 노트다 —
> 발견·파싱 계층이 어떻게 갈라져 있고, **새 문서 종류를 하나 더 읽으려면 무엇을 어떤 순서로
> 건드리는지**를 적어 두었다. 티켓 02·03 은 그 절차를 밟는다.

### 1. 무엇이 프로젝트인가

`.cling/profile.md` 대신 **루트 `AGENTS.md` 와 `docs/features/` 디렉토리를 둘 다 가진 디렉토리**를
프로젝트로 센다(F10). 스캔 뿌리 기본값은 `~/Documents` 에서 **`~/Documents/ai2/projects`** 로 좁힌다.
`GOOTTE_ROOTS` 로 덮어쓰는 성질은 그대로 둔다.

둘 다 요구하는 이유: `AGENTS.md` 만 보면 firstmate 저장소 자신과 각종 격리 사본까지 딸려 들어오고,
`docs/features/` 만 보면 아직 firstmate 관리가 아닌 저장소가 섞인다.

### 2. 할일 목록은 어디서 오는가

`docs/features/<기능>/issues/<NN>-<슬러그>.md` 를 전부 읽어 기능별 목록을 만든다.
파일당 뽑는 것은 번호·제목·`Status:` 값·`Blocked by:` 목록 네 가지다(F4).
`Blocked by:` 에 나열된 번호가 전부 `resolved` 면 **막힘 해제**로 계산한다(F5) — 파일에 그렇게 적혀 있지
않아도 계산으로 나온다. 이것이 INV-1 이 말하는 파생물이다.

`spec.md` 는 기능 단위의 표제와 상태를 준다. 같은 여덟 값을 쓴다.

### 3. "처리중" 은 파일이 아니라 격리 사본이 말한다

**정규 여덟 값에 처리중이 없는 것은 결함이 아니라 설계다**(F5) — 누가 지금 붙들고 있는지는 파일에 손으로
적을 것이 아니라 관측할 것이다. 관측 지점이 `~/.treehouse` 다.

판정: `<뿌리>/<프로젝트>-<6자리>/*/` 각 슬롯에서 **HEAD 가 브랜치에 있으면 작업중, detached 면 유휴**(F7).
뿌리는 `GOOTTE_TREEHOUSE` 로 덮어쓸 수 있게 해 기계 종속을 피한다.

남는 문제는 **그 작업이 어느 티켓인가**다. 브랜치 슬러그가 번호를 담지 않는다(F8·F9).

| 안 | 방법 | 결정적인가 | 대가 |
|---|---|---|---|
| **A** | 브랜치 이름 규약을 `fm/<기능>--<NN>-<슬러그>` 로 못박고 파싱 | ✅ | **firstmate 쪽 규약 변경이 필요하다** — 이 저장소가 정할 수 없다 |
| **B** | 그 브랜치의 커밋이 건드린 `docs/features/<기능>/issues/<NN>-*.md` 경로로 역추적 | ✅ | 그 작업이 티켓 파일을 건드릴 때만 잡힌다 |
| C | 브랜치 슬러그와 티켓 슬러그를 비슷한 정도로 맞춰봄 | ❌ | INV-4 위반 |
| D | firstmate 사설 홈의 작업 기록을 읽음 | ✅ | 남의 사설 홈에 손을 뻗고 이 기계에만 통한다 |

**B 를 1차로 짓는다.** 규약 변경 없이 오늘 동작하고 결정적이다. A 는 더 튼튼하지만 firstmate 쪽 결정이라
이 사양이 혼자 약속할 수 없다 — 캡틴이 그 규약을 넣기로 하시면 그때 A 를 우선 규칙으로 얹는다(결정 Q1).

**매핑에 실패한 작업중 슬롯은 감추지 않는다.** "티켓 미상 · 작업중" 으로 정직하게 센다.
조용히 빠뜨리면 화면이 "아무도 아무것도 안 하는 중" 이라고 거짓말한다.

Q3 의 사상 규칙 — `resolved` → `done`, `wontfix` → `dropped`, 격리 사본에서 관측된 처리중 → `in_progress`,
나머지 다섯 값 → `pending`. **원문 여덟 값은 별도 칸에 그대로 실어** 화면이 `blocked` 와 `needs-info` 를
구분해 보여줄 수 있게 한다. 뭉개는 쪽이 아니라 함께 싣는 쪽이다.

## 티켓 04 의 전제가 틀렸다 (2026-08-09, 착지 시 기록)

**티켓 04 는 옛 읽기 경로를 "이제 아무도 쓰지 않는 코드" 로 적었다. 그것은 사실이 아니었다.**
착수 시점에 그 경로는 여전히 배선돼 있었다 — `loadProjectState` 가 10개 라우트 중 8개를 먹이고 있었고,
대시보드의 **기본 탭이 그 경로 위의 `plan`** 이었으며, `pnpm plan`·`pnpm lineage`·`pnpm digest`
세 명령과 `.gootte/PLAN.md` 산출까지 같은 뿌리에 매달려 있었다.

정확히 말하면 **죽은 코드가 아니라 굶은 코드**였다. 관리대상 프로젝트 어디에도
`docs/roadmap`·`docs/todo`·`docs/sprint` 가 남아 있지 않아 입력이 0이었을 뿐,
코드 경로 자체는 살아서 빈 결과를 렌더하고 있었다.

그래서 **티켓의 두 조건이 서로 충돌했다** — "그 경로를 전부 지운다" 와 "화면은 그대로다" 는
동시에 참일 수 없었다. 제거는 탭 3개 중 2개와 CLI 3개를 함께 데려가고, 그것은 제품 표면에 대한
결정이지 구현자가 혼자 내릴 판단이 아니다. 그래서 크루가 멈추고 캡틴께 올렸고,
