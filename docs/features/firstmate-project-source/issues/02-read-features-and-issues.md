# 02 — 할일 목록을 기능 문서에서 읽는다

**What to build:** 프로젝트를 골랐을 때 **무엇이 남았고 무엇이 막혀 있는지**를 보여준다.
자료는 각 기능 폴더의 사양 문서 한 장과 그 아래 티켓 파일들이다.
티켓의 상태와 선행 조건을 읽고, **막힘이 풀렸는지는 계산한다** — 파일에 그렇게 적혀 있지 않아도.

**Blocked by:** 01

**Status:** resolved (2026-08-09)

## 완료 시 시연 가능한 것

캡틴이 대시보드에서 jinwooauto 를 고르면 **기능별로 묶인 할일 목록**이 뜬다.
각 항목에 상태가 붙어 있고, 선행 티켓이 전부 끝난 항목은 **막힘이 풀린 것으로 보인다.**
선행이 남은 항목은 무엇을 기다리는지 보인다.

## 완료 조건

- 기능 폴더 하나에서 사양 문서의 표제와 상태를 읽는다.
- 티켓 파일에서 네 가지를 뽑는다 — 번호, 제목, 상태, 선행 티켓 목록.
- **상태 어휘 사상**은 다음과 같다. 원문 여덟 값을 뭉개지 않고 **한 칸 더 실어 보낸다.**

  | 원문 상태 | 기존 다섯 값 | 원문 칸 |
  |---|---|---|
  | 완료 | `done` | 그대로 보존 |
  | 처리 안 함 | `dropped` | 그대로 보존 |
  | 나머지 여섯 | `pending` | 그대로 보존 |

  `in_progress` 는 **이 티켓이 만들지 않는다** — 그것은 문서가 아니라 관측에서 나오고, 티켓 03 의 몫이다.
  원문 칸을 함께 싣는 이유는 화면이 "외부 요인으로 대기" 와 "정보 부족" 을 구분해 보여줄 수 있어야 하기 때문이다.
- **막힘 해제 계산** — 선행으로 나열된 번호가 전부 완료면 그 티켓은 착수 가능으로 계산된다.
  이 값은 어디에도 저장하지 않는다. 볼 때마다 다시 계산한다.
- 완료 상태에 붙는 완료일을 함께 읽는다.
- `pnpm verify` green.

## 테스트

**이 티켓이 이 형식을 처음 덮는다.** firstmate 문서를 읽는 테스트는 지금 하나도 없다.

파싱 규칙은 **순수 계층 단위 테스트**가 소유한다. 여기서 깨지면 위 어디서도 살 수 없기 때문이다.
반드시 포함할 경우:

| 입력 | 기대 |
|---|---|
| 여덟 상태 값 각각 | 위 표대로 사상되고 원문이 보존된다 |
| 상태 줄 뒤에 괄호 사유나 날짜가 붙음 | 값만 뽑고 나머지에 넘어가지 않는다 |
| 선행이 전부 완료 | 착수 가능으로 계산된다 |
| 선행 중 하나가 미완 | 막힘으로 계산된다 |
| 선행 줄이 없음 | 즉시 착수 가능 |
| 알 수 없는 상태 문자열 | **조용히 버리지 않는다.** 무엇이 이상한지 드러난다 |

마지막 줄이 중요하다. 상태를 못 읽어 항목이 목록에서 사라지면 화면이 "할 일이 없다" 고 거짓말한다.

파일 읽기는 IO 계층에서 임시 디렉토리 픽스처로 덮고, 화면은 목록이 뜨는지까지만 얇게 덮는다.

## 이 티켓이 하지 않는 것

- 처리중 판정 — 티켓 03. 여기서는 그 값이 나오지 않는다.
- 결정 기록(`adr/`) 읽기. 이번 범위 밖이다.
- 관리대상 문서에 쓰기 — 상태를 그 파일에 적어 넣는 것도 여기 포함된다. **읽기만 한다.**
- 프로젝트마다 다른 서식 지원. 지금은 한 관례만 읽는다.
