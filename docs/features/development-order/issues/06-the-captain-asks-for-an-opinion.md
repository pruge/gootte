# 06 — 캡틴이 의견을 청하고 답을 그 자리에서 본다

**What to build:** `plan` 탭에서 판단이 필요한 것이 생기면 **[의견 물어보기] 버튼**이 뜬다.
누르면 요청 한 줄이 남고, planner 의 답이 **그 배치 옆에 붙는다.**
캡틴은 대화창으로 옮겨 가지 않으신다.

**Blocked by:** [04](04-the-captain-drags-to-change-the-order.md) — 버튼이 드래그 화면 위에 산다

**Status:** claimed

## 캡틴 지시 (2026-08-11, 원문)

> a.ticket1 -> b.tiket1 -> a.tiket2 가 되는 경우도 있는데. 그때는 네가 자동으로인지 하여 의견을 말했으면한다.
> firstmate가 메시지를 확인하듯이 background에서 넘겨주는 방식도 괜찮고. 아니면 버튼을 두어 네게 알리도록해도 좋고.

**캡틴 결정 (2026-08-11):** 채팅창이 아니라 **한 왕복만.** *“이대로 가자.”*

## 🔴 인지는 자동, 전달은 버튼

캡틴이 주신 두 안 중 **버튼**이다. 다만 **버튼이 언제 뜨는지는 기계가 판단한다** —
캡틴이 무엇을 물어야 할지 아실 필요가 없다.

🔴 **드래그마다 planner 를 부르면 안 된다.** 자리 하나 잡으려 다섯 번 끄시면 그중 넷은
**캡틴이 이미 버린 배치**다 — planner 가 낡은 의도에 대고 의견을 말하게 되고,
그것이 이 기능이 없애려는 통증과 같은 종류다.

버튼이 뜨는 조건(기계가 정한다):

| 조건 | 예 |
|---|---|
| 엇갈림이 생겼다 | 한 기능의 티켓 사이에 다른 기능이 끼어든다 |
| 병렬이 새로 생겼다 | 서로 다른 기능의 티켓이 같은 단계에 놓였다 — 정말 무관한가 |
| 이유가 뒤집혔다 | `왜_확인필요` 가 선 것이 있다(티켓 04) |

🔴 **04 의 즉시 검사와 섞지 마라.** 저것은 기계가 아는 사실이라 그 자리에서 끝나고,
이것은 **판단**이라 사람에게 간다. 화면에서도 두 덩이가 구분돼야 한다.

## 표

| 표 | 키 | 칸 |
|---|---|---|
| `opinion_request` | 요청 id | 프로젝트 · 배치 요약 · 물음 · 답 · 처리됨 · `updated_at` |

**배치 요약**은 버튼을 누른 **그 순간의 배치**를 담는다 — 나중에 캡틴이 더 끄셔도
planner 가 무엇에 대해 답하는지 흔들리지 않는다.

## 명령

```
gootte-axi ask                      🔴 대기 중일 때만 한 줄, 없으면 침묵
gootte-axi ask show   <id>          배치 요약과 물음 전체
gootte-axi ask answer <id> --say "…"                    (전부 --json)
```

🔴 **티켓 05 의 `extra` 와 같은 규약이다** — 있을 때만 한 줄, 없으면 침묵, 제한 시간 안에 끝난다.
firstmate 의 사용자 정의 확인 장치 **하나**로 둘 다 깨어난다.
🔴 **새 데몬도 새 통로도 만들지 마라.**

## 화면

**버튼** — 물어볼 것이 있을 때만, 그 자리에. 누르면 요청이 남고 버튼이 *보냈습니다* 로 바뀐다.

**답** — 도착하면 그 배치 옆에 한 덩이로 붙는다. 누가(planner) · 언제 · 본문.
🔴 **답 본문을 요약하지 마라 — verbatim 으로 싣는다**(INV-4).

🔴 **채팅창을 만들지 마라.** gootte 는 planner 를 부를 수 없다 —
버튼은 줄 하나를 남길 뿐이고 firstmate 가 그것을 옮긴다. **분 단위이지 초 단위가 아니다.**
대화창 모양은 화면이 지킬 수 없는 약속을 하게 만들고, 캡틴은 오지 않는 답을 기다리시게 된다.
**한 왕복만 그린다.** 되물을 것이 있으면 버튼을 다시 눌러 새 요청을 만든다.

🟡 답을 기다리는 동안 그 사실이 보여야 한다 — 눌렀는지 안 눌렀는지 캡틴이 헷갈리지 않게.

## 완료 시 시연 가능한 것

캡틴이 티켓 칩을 끌어 엇갈림을 만든다. 그 자리에 ⚡ 와 **[의견 물어보기]** 가 뜬다. 누른다.
firstmate 가 그것을 알아채고 planner 에게 넘긴다. planner 가 `ask answer` 로 답한다.
캡틴이 `plan` 탭을 다시 열면 **그 배치 옆에 답이 붙어 있다.**

## 완료 조건

- [ ] 물어볼 것이 있을 때만 버튼이 뜬다. 없으면 안 뜬다
- [ ] 조건 셋(엇갈림 · 새 병렬 · 뒤집힌 이유)이 각각 버튼을 띄운다
- [ ] 🔴 판단 요청과 04 의 즉시 검사가 화면에서 **구분된다**
- [ ] 요청에 **누른 순간의 배치 요약**이 담긴다
- [ ] `ask` 가 대기 중일 때만 한 줄, 없으면 침묵한다
- [ ] 답이 **verbatim** 으로 그 배치 옆에 붙는다
- [ ] 답을 기다리는 상태가 화면에 보인다
- [ ] 🔴 채팅창이 **아니다** — 한 요청에 한 답, 스레드 없음
- [ ] 🔴 `next` 계산이 이 표를 **안 본다**

## 이 티켓이 하지 않는 것

- **캡틴 눈 확인** — 화면 모양은 티켓 04 가 확인한 것을 그대로 쓴다. 새 확인 항목을 만들지 않는다.
- **채팅·스레드·실시간 밀어 주기** — 별건이다. 필요해지면 그때 새 기능으로 적는다.
- **planner 를 화면이 직접 부르는 일** — 못 한다. firstmate 가 옮긴다.
- **답을 기계가 만드는 일** — 판단은 사람 몫이다(INV-4).
