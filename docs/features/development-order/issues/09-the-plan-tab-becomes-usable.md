# 09 — `plan` 탭을 캡틴이 실제로 쓸 수 있게 만든다

**What to build:** 캡틴이 `plan` 탭을 쓰시면서 부딪힌 것 넷을 **한 번에** 고친다 —
쓸모없는 상자를 걷어내고, 남은 상자들이 서로 구분되게 하고, 단계 보기를 기능 보기처럼
세로 칸으로 바꾸고, 조작 줄이 스크롤해도 화면에 남게 한다.

**Blocked by:** 없음 — 지금 착수 가능

**Status:** resolved (2026-08-11)

## 🔴 왜 한 티켓인가

넷 다 **같은 화면(`plan` 탭)**, 같은 사람, 그리고 **같은 캡틴 확인 한 번**이다.
쪼개면 파이프라인을 네 번 돌리고 캡틴을 네 번 부른다 — 그런데 캡틴은 한 번에 한 화면만
확인하실 수 있으므로 **나머지 셋은 작업자가 사본만 잡고 기다린다.**

그리고 **서로 얽혀 있다.** ①이 지울 상자를 ②가 다듬으면 일이 두 번 된다.
🔴 **①을 먼저 하고 나머지를 그 위에서 한다.**

| | 무엇 | 캡틴 지시 (2026-08-11, 원문) |
|---|---|---|
| ① | 의견 물어보기를 **걷어낸다** | "저게 맨 위에 있으면 정작 봐야할 내용이 뒤로 밀리잖아. **아예 없애.**" |
| ② | 주황색 상자 둘이 **구분되고**, 경고가 스스로 사라진다 | "어긋나는 것이 없으면 주황색 box가 안보였었는데. 지금은 없는데도 남아 있네." |
| ③ | 단계 보기 — **3열 그리드는 그대로, 칸은 단계·칸 안은 트랙별 묶음** | "3column 그대로 두고 단계와 track 위치만 바꾸면 되는것을." (실물을 두 번 보신 뒤의 정정 — §③ 참고) |

## ① 의견 물어보기를 걷어낸다

### 🔴 요청을 거꾸로 만들었다

티켓 06 의 출발점은 캡틴의 이 말이었다:

> "그때는 **네가 자동으로 인지하여 의견을 말했으면** 한다.
> background에서 넘겨주는 방식도 괜찮고. 아니면 버튼을 두어 네게 알리도록해도 좋고."

**planner 가 알아채고 planner 가 말한다** — 그것이 요청이었고, 버튼은 나르는 방법 중 하나였다.
만들어진 것은 반대다:

| 캡틴이 요청하신 것 | 만들어진 것 |
|---|---|
| planner 가 알아채서 **말해 준다** | 캡틴이 상자를 발견하고 **누르러 가신다** |
| 캡틴은 아무것도 안 하신다 | 누를지 판단하고, 기다리고, 화면으로 **돌아와 확인**하신다 |

그리고 캡틴과 planner 는 **이미 대화 창에서 이야기한다.** 거기서는 맥락 전부를 갖고 몇 초 만에
답이 오간다. 이 화면은 그것의 **느리고 얇은 판본**이었고, 그 대가로 **계획이 아래로 밀렸다.**
🔴 **더 나은 통로가 이미 있는데 못한 통로를 화면 맨 위에 세우면 안 된다.**

### 지울 것

| 어디 | 무엇 |
|---|---|
| 화면 | 의견 요청 상자(패널 컴포넌트)와 그것을 부르는 자리 |
| 서버 | 의견 요청을 받고 내주는 경로 |
| 저장 | `opinion_request` 표와 그 저장 코드 |
| 계산 | 버튼이 뜰 조건을 판단하는 순수 함수 |
| 터미널 | `ask` · `ask show` · `ask answer` 와 사용법 줄 |
| 타입·테스트 | 위에만 쓰이던 것들 |

🔴 **상자만 지우고 계산을 남기지 마라.** 아무도 안 쓰는 코드와 아무도 안 읽는 표가 남으면
다음 사람이 그것을 되살릴 근거로 삼는다.

🟢 되살리기는 언제든 싸다 — 이 절과 06 이 이유를 갖고 있다. 필요해지면 그때
**planner 가 먼저 말을 거는 모양**으로 새로 쓴다. 버튼으로 되돌리지 않는다.

🔴 **06 티켓 파일은 지우지 마라.** 착지한 기록이고, 왜 되돌렸는지가 거기 있어야 한다.
맨 위에 09 가 걷어냈다는 줄만 붙인다.

## ② 주황색 상자 하나가 서로 다른 두 가지를 말한다

### 🔴 캡틴이 보신 것은 어긋남 상자가 아니었다

그때 어긋남은 실제로 0 이었다 — 살아 있는 서버에 물어 확인했다:

| 확인한 것 | 결과 |
|---|---|
| `gootte order jinwooauto` | `어긋남: 없음` |
| 떠 있는 서버 `/api/plan/jinwooauto` | `mismatches: 0`, 빈 배열 |
| 어긋남 목록 컴포넌트 | 0 건이면 아무것도 안 그린다 — **정상 동작** |

남아 있던 것은 **드래그 경고 상자**다. 🔴 **둘이 같은 옷을 입고 나란히 서 있다.**

| | 어긋남 | 드래그 경고 |
|---|---|---|
| 테두리·배경·모서리·글자색 | `partial` 계열 | **똑같다** |
| 자리 | `plan` 탭 위쪽 | **바로 붙어 있다** |
| 뜻 | 계획과 티켓이 갈라졌다 | 방금 그 드래그가 뭔가에 걸렸다 |
| 언제 사라지나 | 어긋남이 없어지면 자동 | 🔴 **캡틴이 ✕ 를 누를 때만** |

**캡틴이 하나를 다른 하나로 읽으신 것은 착각이 아니라 화면의 결함이다** —
구분 불가능하게 생겼으면 구분해서 보라고 요구할 수 없다.

🔴 **이 결함은 06 이 이미 예고했다**(*"04 의 즉시 검사와 섞지 마라 … 화면에서도 두 덩이가
구분돼야 한다"*). 그 규칙이 06 에만 적용되고 **02 의 어긋남과 04 의 경고 사이에는 안 적용됐다.**

### 고칠 것 둘

**경고가 스스로 없어진다.** 지금은 드롭 성공 시 세팅되고 ✕ 로만 지워진다. 그래서
캡틴이 곧바로 다시 끌어 문제를 없애도, 계획이 다른 경로(터미널 · 티켓 08 의 자동 제거)로
바뀌어도 그대로 남는다. 🔴 **경고는 그 시점의 배치에 대한 말이므로, 배치가 바뀌면 더 이상
참이 아니다.** 다시 성립하지 않는 경고는 스스로 없어져야 한다.

🔴 **판정을 화면에서 새로 짜지 마라.** 네 검사는 이미 서버(`checkTicketDragWarnings`)가
계산한다 — 화면이 다시 판정하면 그 순간 두 답이 생기고 하나는 거짓이다. **다시 물어서 갱신한다.**

🟡 **✕ 는 남긴다.** 캡틴이 알면서 그대로 두시는 것이 정당할 수 있고(티켓 04),
닫은 것은 배치가 다시 바뀌기 전까지 닫힌 채로 있어야 한다.

**둘이 서로 다르게 생긴다.** 🔴 **색만 바꿔 때우지 마라.** 차이는 색이 아니라 성격이다:

| | 어긋남 | 드래그 경고 |
|---|---|---|
| 무엇에 대한 말인가 | **계획 전체**의 상태 | **방금 한 동작** 하나 |
| 언제 생기나 | 계획이나 티켓이 바뀔 때 | 캡틴이 놓는 순간 |
| 놓칠 때의 대가 | 계획이 조용히 낡는다 | 이번 드래그가 조금 어긋난다 |

**항상 있는 것**과 **방금 일어난 것**이 같은 무게로 보이면 안 된다.
모양은 구현자가 정하되, **위 성격 차이가 읽히는지**가 판정 기준이다.
🔴 **어긋남을 접거나 숨기지 마라**(티켓 03) — 그 규칙은 안 건드린다.

## ③ 단계 보기 — 카드는 단계, 그 안은 트랙별 묶음

### 캡틴 지시 (2026-08-11, 원문)

> "단계에서 track의 영역을 ticket이 침범하지 못하게해."

> "단계 보기도 기능 보기 처럼 해. 3column으로 배치하고 그안에 ticket들 놓는것 처럼."

🔴 **후속 지시 둘(같은 날, 구현을 보신 뒤)이 배치를 두 번 더 정했다:**

> "**단계 보기에서. 카드는 단계를 표시하고 그 안에 track 별 ticket으로 묶어 표시하라.**"

> "**야. 3column 그대로 두고 단계와 track 위치만 바꾸면 되는것을.**"

두 번째 지시(카드=단계)를 구현하며 세로 칸 얼개 자체를 버리고 카드를 위아래로 쌓았더니,
세 번째 지시가 그건 과했다고 바로잡았다 — **3열 그리드는 그대로 두고, 칸(열)이 트랙이던
것을 단계로, 칸 안의 내용물이 단계였던 것을 트랙으로 — 자리만 맞바꾸면** 될 일이었다.
최종 배치: **3열 그리드는 유지, 칸(열) = 단계, 칸 안 = 트랙별 묶음.**
첫 지시("트랙 영역을 티켓이 침범하면 안 된다")는 여전히 풀린다 — 트랙 라벨이 칩과 같은
줄을 공유하지 않고 라벨 위·칩 아래로 블록을 쌓으므로 침범할 줄 자체가 없다.

### 무엇으로 바꾸나

기능 보기와 **같은 3열 그리드**(넓으면 세 칸, 좁아지면 두 칸·한 칸)를 그대로 쓴다.
**칸 하나 = 단계 하나.** 칸은 단계 번호 순서대로 놓인다(그리드가 접히면 다음 줄로 넘어간다).
칸 안에서는 **그 단계에 티켓이 있는 트랙만** 묶음으로 나뉘어 위에서 아래로 쌓인다 —
트랙 이름이 라벨로 먼저 서고, 그 아래 그 트랙·그 단계의 티켓 칩들이 놓인다.

```
┌ 단계 1 ────────┐ ┌ 단계 2 ────────┐ ┌ 단계 3 ────────┐
│ 웹·권한        │ │ 게이트웨이 제어 │ │ 웹·권한        │
│  칩 칩         │ │  칩 칩          │ │  칩            │
│ 낱개           │ └─────────────────┘ └─────────────────┘
│  칩 칩 칩      │
│ 게이트웨이 제어│
│  칩            │
└─────────────────┘
```

- 어느 단계에 아무 트랙도 없으면(있을 수 없다 — 단계는 티켓이 있어야 생긴다) 그 칸
  자체가 없다. **없는 트랙 묶음을 빈 칸으로 그리지 않는다.**
- 🔴 **칩이 자기 묶음을 안 넘는다.** 긴 제목·긴 티켓 번호는 잘리고 가로로 흘러넘치지 않는다
  (좁은 창에서도 — `TicketChip` 의 두 span 이 함께 truncate 한다).
- 🔴 **트랙을 한 줄로 펴지 마라**(티켓 03 금지 조항) — 라벨과 칩이 같은 줄을 공유하지
  않으므로 이 규칙을 여전히 지킨다.

### 드래그는 그대로 동작한다

- 칩을 **같은 카드의 다른 트랙 묶음**으로 끌면 → 그 티켓이 속한 **기능의 트랙**이 바뀐다.
  🟡 기능 보기에서 카드를 다른 칸으로 끄는 것과 같은 뜻이다.
  🔴 **트랙은 기능이 갖는다** — 티켓 하나만 다른 트랙으로 보낼 수는 없다.
  그 사실이 화면에서 읽혀야 하고, 읽히지 않으면 그 조작은 **막는 대신 무슨 일이 일어나는지
  먼저 알려라.**
- 칩을 **다른 단계 카드**로 끌면 → 단계가 바뀐다(같은 카드 안이면 트랙도 함께).
- 칩을 **카드와 카드 사이**로 끌면 → 새 단계가 생긴다(티켓 04).

🔴 **놓을 자리가 끄는 동안 보여야 한다**(티켓 04 캡틴 확인 1).

### 🟢 기능 보기는 안 바꾼다

이미 캡틴이 원하시는 꼴이다(트랙마다 세로 칸). **단계 보기도 같은 3열 그리드 얼개를 쓴다** —
다만 칸의 정체가 다르다: 단계 보기 = 칸(단계)+묶음(트랙), 기능 보기 = 칸(트랙)+카드(기능).
🔴 **그리드 껍데기(반응형 3→2→1 열)는 두 벌 짓지 않는다** — 같은 Tailwind 그리드 클래스를
그대로 쓴다. 트랙 발견 방식(`order.features` 의 트랙 ∪ 티켓이 가리키는
트랙, `localeCompare` 정렬)은 두 보기가 같은 규칙을 쓴다 — 그 부분만 같은 재료다.

## ④ 보기 전환과 `next` 가 스크롤해도 남는다

### 원인

`plan` 탭이 **통째로 하나의 스크롤 영역**이고 조작 줄이 **그 안의 첫 자식**이다.
계획을 훑어 내려가면 조작 줄도 같이 밀려 올라간다.

**왜 아픈가:** 계획이 길수록 아래에서 보내는 시간이 긴데, **정작 거기서 보기를 바꾸거나
`next` 를 누르고 싶어진다.** 맨 위까지 올라갔다 누르고 다시 내려와 보던 자리를 찾아야 한다.
🔴 **목록이 길수록 나빠지는 종류의 결함**이다.

### 무엇을 바꾸나

🔴 **조작 줄은 스크롤 대상이 아니다.** 계획만 스크롤하고 조작 줄은 제자리에 있는다.
단계·기능 보기 전환, `next` 버튼, "되돌리기 없음" 표시가 함께 남는다.

- 🔴 **가로 스크롤을 만들지 마라.** 좁은 창에서 접히더라도 옆으로 밀려나면 안 된다.
- 🔴 **본문을 가리지 마라.** 붙어 있는 줄 아래로 첫 단계가 반쯤 숨으면 안 된다.
- 🟡 밑을 지나가는 계획이 **비쳐 보이면 안 된다** — 붙박이가 아니라 고장으로 읽힌다.
- 🟡 조작 줄이 **지금보다 두꺼워지지 않게** 한다. 계획 볼 자리가 줄어든다.

🟢 **`features` 탭도 같은 얼개인지 보고, 같으면 같이 고친다** — 두 탭이 다르게 움직이면
그 차이 자체가 다음 질문거리가 된다.

## 🔴 넷 모두에 걸리는 금지

- **`extra` 를 건드리지 마라.** `ask` 와 `extra` 는 firstmate 를 깨우는 같은 규약을 쓰지만
  다른 물건이다. `ask` 가 사라져도 **`extra` 는 그대로 동작해야** 하고 firstmate 가 여전히 깨어난다.
- **드래그의 네 검사(티켓 04)를 없애지 마라.** 캡틴이 지목하신 것은 의견 요청 상자뿐이다.
- **`next` · 어긋남 · 단계 · 순위 계산 결과가 하나도 바뀌면 안 된다.**
  ①은 빼기만, ②③④는 배치와 수명만 고친다.
- **트랙을 한 줄로 펴지 마라**(티켓 03 금지 조항).
- **`features` 탭의 동작을 바꾸지 마라** — ③④의 "같으면 같이 고친다"는 **같은 결함의 수리**이지
  개편이 아니다.

## 완료 시 시연 가능한 것

캡틴이 `plan` 탭을 연다. **맨 위에 의견 요청 상자가 없고**, 순서를 아무리 끌어 바꿔도 안 나타난다.
어긋남도 경고도 없을 때 **주황색 상자가 하나도 없다.** 티켓 칩을 막힘 역행이 되게 끌면 경고가
뜨고, 곧바로 되돌리면 **스스로 사라진다.** 일부러 어긋남을 만들면 그 상자는 경고와 **한눈에
다르게** 생겼다. 단계 보기는 **3열 그리드의 칸이 단계**이고 칸 안에서 **트랙별로 묶여** 나타난다.
계획을 맨 아래까지 내려도 **보기 전환과 `next` 가 화면에 그대로 있어** 거기서 바로 누를 수 있다.
`gootte ask` 는 없는 명령이고, `gootte extra` 는 그대로 동작한다.
