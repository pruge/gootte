## `next` 의 정의

**트랙마다** — 트랙은 병렬이고 다루는 사람이 다르므로 각각 따로 답한다:

1. 계획된 단계를 오름차순으로 훑어 **가장 앞선 미완료 단계**를 찾는다.
   (그 단계의 티켓이 전부 완료면 다음 단계로 넘어간다)
2. 그 단계에서 **완료가 아니고, 막히지 않았고, 임자가 없는** 티켓 전부를 돌려준다.
3. 그것이 곧 **동시에 보낼 수 있는 목록**이다.

🟢 **재료가 이미 다 있다.** 막힘·임자 판정은 `core/src/project/features.ts` 의 `toTicket` 이
`startable = waiting.length === 0 && !claimed` 로 이미 계산한다.
🔴 **그 판정을 새로 만들지 마라** — 이미 계산된 값을 읽는다(INV-1). 판정 자리는 하나뿐이다
(`contract/src/index.ts` §`FeatureTicket.startable` 이 같은 이유로 세운 규율).

🔴 **빈 결과에 이유를 붙인다.** 그냥 빈 목록을 돌려주면 읽는 쪽이 *"할 일이 없다"* 와
*"전부 막혔다"* 를 구분할 수 없고, 그것이 §실측 의 통증과 같은 종류의 거짓말이다.
구분해야 할 것: 전부 막힘 / 전부 임자 있음 / 단계가 하나도 안 적혔다 / 정말 다 끝났다.

## 어긋남 세 줄 — 감추지 않는다

계획(DB)과 티켓(관리대상)은 이제 **따로 움직인다.** 티켓은 크루의 PR 로, 단계는 DB 로 간다.
같은 커밋에 실리지 않으므로 리뷰가 잡아 주지 못한다. **대신 읽는 쪽이 큰 소리로 말한다.**

| 어긋남 | 뜻 |
|---|---|
| **단계 없는 티켓** | 새로 썼는데 계획에 안 넣었다 |
| **티켓 없는 단계** | 티켓이 사라졌거나 번호가 바뀌었다 |
| **끝났는데 앞 단계에 남은 것** | §실측 의 넷이 이 줄로 잡혔을 것이다 |

🟢 이 저장소에 이미 있는 문화 그대로다 — `unknown` · `unreadable` · `unclaimed` 를
감추지 않는 것과 같은 원리다(`contract/src/index.ts`).

`order` 는 이 티켓에서 어긋남을 함께 싣도록 늘어난다.

## 🔴 순수 함수로 짓는다

`next` 계산은 **`core` 의 순수 함수**로 둔다. 입력은 이미 만들어진 `Feature[]` 와 계획 줄들,
출력은 트랙별 묶음이다.

- I/O 에 묶으면 테스트가 파일시스템을 타고,
- 무엇보다 **화면(티켓 03)의 `next` 버튼이 같은 함수를 써야 한다.** 두 곳에서 각자 판정하면
  터미널과 화면이 다른 답을 하고, 그 순간부터 하나는 거짓이다.

## 완료 시 시연 가능한 것

firstmate 가 터미널에서 `gootte-axi next jinwooauto` 를 치면
**트랙별로 묶인, 지금 동시에 보낼 수 있는 티켓 목록**이 나온다. 각 줄에 왜 그 단계인지 한 줄이 붙는다.
한 티켓이 `resolved` 로 착지한 직후 같은 명령을 다시 치면 **다음 것이 저절로 나온다** — 아무도 아무것도 안 적었는데.
