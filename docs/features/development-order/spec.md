## 모델 — 단계 하나로 순서와 병렬을 함께 적는다

> **같은 단계 = 병렬 가능. 단계가 다르면 = 순서.**
> 티켓에 정수 하나. 그것이 전부다.

캡틴 예시가 그대로 표현된다. 기능 `a` 만 있을 때 —

```
단계 1  a/1   단계 2  a/2   단계 3  a/3   단계 4  a/4
```

개발 중 부족한 것이 나와 기능 `b` 를 새로 등록하면 계획을 다시 적는다:

```
단계 1  a/1        단계 3  b/1        단계 5  b/3        단계 6  a/3
단계 2  a/2        단계 4  b/2                          단계 7  a/4
                          ↑ b/2 와 b/3 이 서로 무관하면 같은 단계로 합친다 = 병렬
```

🟢 **기능이 끊겼다 다시 나오는 것이 정상이다.** `a` 가 앞 단계에 있다가 `b` 뒤로 이어진다 —
단계는 기능을 가로지르므로 엇갈림에 따로 장치가 필요 없다.

### 세 층

| 층 | 무엇 | 바뀌는 빈도 |
|---|---|---|
| **트랙** | 병렬로 굴러가는 갈래. **다루는 사람이 다르다** | 거의 안 바뀜 |
| **기능 순위** | 트랙 안에서 어느 기능을 먼저 끝낼 것인가 | 가끔 |
| **티켓 단계** | 오늘 무엇을 나란히 집어가나 | 매일 |

🔴 **기능 순위는 제약이 아니라 동점 처리다.** 순위가 티켓을 가두면 엇갈림이 원천적으로 불가능해진다.
순위는 표시 묶음과 같은 단계 안의 줄 세우기에만 쓴다.

🔴 **순위는 성기게(10·20·30) 매긴다.** 두 이웃의 중간값 하나만 쓰면 되므로 **줄 하나만 바뀐다.**
촘촘한 1·2·3 은 하나 끼울 때마다 전부 밀리고, 그 밀림이 곧 낡음이다. 틈이 다 차면 그 트랙만 다시 매긴다.

### 막힘과 단계는 다른 것이다

| | 무엇 | 어디서 오나 |
|---|---|---|
| **막힘** | 물리적으로 불가능하다 | 티켓의 `Blocked by:` — 기계가 읽는다(S1) |
| **단계** | 이렇게 하는 편이 낫다 | 계획. DB 에 적는다 |

`next` 는 **둘을 곱한다.** 🔴 **DB 에 의존 관계를 또 적지 않는다** — 이미 티켓에 있다.

## 🔴 완료는 저장하지 않는다 — 그래야 실시간이 된다

캡틴 말씀 중 *“firstmate가 보고 완료 처리하는 거지”* 한 대목만 다르게 푼다.

**완료를 DB 에 적으면 그 순간 `next` 가 실시간이 아니게 된다** — 누군가 적어 줘야 갱신되고,
안 적으면 §문제 의 그 표가 다시 생긴다.

> **firstmate 의 “완료 처리” 는 PR 을 착지시키는 것 자체다.**
> 티켓 파일이 `resolved` 가 되고 gootte 가 그것을 읽는다. 아무도 아무것도 적지 않는다.

🟢 캡틴이 바라신 *“그 시점에 next는 실시간으로 다음 할 수 있는 것을 알게 되겠지”* 가
**저장하지 않음으로써** 이루어진다.

## 저장 형태 — 표 넷 + 파일 하나

**덮어쓰기 — 항상 최신만**

| 표 | 키 | 칸 |
|---|---|---|
| `feature_order` | 프로젝트 · 기능 | 트랙 · 순위 · 왜 · 왜_확인필요 · `updated_at` |
| `ticket_order` | 프로젝트 · 기능 · 티켓 | **단계** · 종류(계획\|틈틈이\|순서밖) · 왜 · `updated_at` |

**큐 — 처리 표시로 소비한다**

| 표 | 키 | 칸 |
|---|---|---|
| `opinion_request` | 요청 id | 배치 요약 · 물음 · 답 · 처리됨 · `updated_at` |
| `extra` | 항목 id | 프로젝트 · 티켓 · 무엇이 더 개발됐나 · 누가 · **처리됨** · `created_at` |

**파일**

`history.md` — 순서 변경 이력(append). 통째로 읽어 흐름을 본다.

🔴 **`왜` 는 필수이고 한 줄이다.** 비워 둘 수 있게 하면 다 비우고, 그러면 남는 게 숫자뿐이라
착지 한 번에 무의미해진다. 길면 티켓에 쓰고 여기서는 가리킨다(캡틴 지시: 세부는 features 문서).
🟢 부수 효과 — 한 줄짜리만 들었으므로 **DB 는 잃어도 되는 물건**이 된다. 그래서 바이너리를
저장소에 넣지 않고 백업 장치도 만들지 않는다.

### 왜 `extra` 는 표이고 `history` 는 파일인가

**소비하는 방식이 다르면 그릇도 달라야 한다.**

- `extra` 는 **항목 하나씩 소비하는 큐**다. 읽고 티켓을 고치면 처리 표시를 남기고,
  다음부터는 새로 등록된 것만 본다 → 표.
- `history` 는 **통째로 읽어 흐름을 보는 것**이다. 같은 것을 두 번 뒤집고 있으면
  그것은 목록이 아니라 흐름에서 보인다 → 순차 텍스트. 그리고 **DB 가 날아가도 남는 유일한 기록**이다.

🔴 **처리 표시는 지우는 것이 아니라 표시다.** 질의 기본값이 미처리만이라 쌓여도 읽기가 느려지지 않는다.
무한히 자라므로 `extra prune` 을 두되 **자동으로 지우지 않는다** — 무엇을 처리했는지가
곧 티켓을 왜 고쳤는지의 근거다.

🟢 `extra` 가 메우는 구멍: **티켓이 낡는 가장 흔한 경로**다. 누가 A 를 하면서 B 의 절반을
같이 만들면 B 티켓은 아무 표시 없이 틀린 문서가 되고, **지금은 그것을 알아채는 장치가 없다.**

## 명령 — `gootte-axi`

```
gootte-axi next  <프로젝트>      지금 나란히 보낼 수 있는 티켓 전부 — 트랙별로 묶어서
gootte-axi order <프로젝트>      단계 전체 + 엇갈림 + 어긋남
gootte-axi ask                  대기 중인 의견 요청 (없으면 침묵)

gootte-axi extra add  <프로젝트> <기능>/<번호> "…"   firstmate: “이것도 같이 개발됐다”
gootte-axi extra                                    미처리만
gootte-axi extra done  <id>
gootte-axi extra prune --before <날짜>

gootte-axi set         <프로젝트> <기능>/<번호> --step 3 --why "…"
gootte-axi set-feature <프로젝트> <기능> --track web --rank 20 --why "…"
gootte-axi drop        <프로젝트> <기능>[/<번호>]
gootte-axi ask answer  <id> --say "…"                          (전부 --json)
```

**`next` 의 정의**: 트랙마다 **가장 앞선 미완료 단계**에서, 막히지도 임자도 없는 티켓 전부.
그것이 곧 firstmate 가 **동시에 보낼 수 있는 목록**이다. 화면의 `next` 버튼과 같은 계산을 쓴다.
결과가 비면 **이유를 말한다**(전부 막힘 / 전부 임자 / 단계가 없음).

🔴 `ask` 와 `extra` 는 같은 규약을 쓴다 — **있을 때만 한 줄 찍고 없으면 침묵.**
firstmate 의 사용자 정의 확인 장치 하나로 둘 다 깨어난다. 새 데몬도 새 통로도 없다.

| 사실 | 확인 |
|---|---|
| 탭 띠는 항목 하나(`features`)지만 **여러 개를 받도록 지어져 있다** | `frontend/src/components/main/Tabs.tsx` `TABS` 배열 |
| 탭 상태는 URL `?tab=` 에 있고 `Tab` 은 union 이다 | `frontend/src/hooks/useUrlState.ts` |
| `view` 는 이미 **탭별 보기 모드**다 — “소비처가 유효값 해소” | 같은 파일 주석 |

→ `?tab=plan&view=step` / `?view=feature`. 🔴 **새 라우팅도 새 상태도 만들지 않는다.**
탭을 바꾸면 `view` 가 초기화되는 기존 동작(`setTab`)이 그대로 맞다.

🟡 **띠에 항목이 둘이 되는 것은 이번이 처음이다** — 지금까지 활성/비활성 대비가 화면에 나타난 적이 없다.
그 대비는 캡틴 눈 확인 항목이다.

### 두 보기, 같은 데이터

- **단계 보기**(기본) — 단계가 가로줄. 같은 줄에 있으면 병렬. 티켓 칩을 줄 사이로 끌면 단계가 바뀌고,
  줄과 줄 사이에 놓으면 새 단계가 생긴다.
- **기능 보기** — 트랙이 세로줄, 기능 카드를 끌어 순위를 바꾼다.

🔴 **트랙은 한 줄로 못 편다.** 병렬이고 다루는 사람이 다르다 — 억지로 한 줄 세우면
나란히 보낼 수 있다는 사실이 화면에서 사라진다.

**`next` 버튼**을 누르면 그 집합이 화면에서 선택된다. CLI 와 같은 계산이다.

🔴 **드래그는 순위·단계만 바꾸고 `왜` 는 안 건드린다.** 대신 그 `왜` 에 **확인 필요** 표시가 붙는다 —
캡틴이 방금 그 이유를 뒤집으셨으니 그 문장은 이제 거짓일 수 있다.

### 두 속도 — 화면이 즉시, planner 는 나중에

| | 누가 | 언제 |
|---|---|---|
| 막힘 역행 · 이미 끝난 것 · 임자 있음 · 낡은 막힘 사유 | 화면(결정적 계산) | 놓는 순간 |
| 병렬로 둬도 되나 · 엇갈림이 맞나 · 뒤집힌 `왜` 를 뭐라 다시 쓸까 | planner | 나중에 |

🔴 **드래그마다 planner 를 부르면 안 된다.** 자리 하나 잡으려 다섯 번 끌면 그중 넷은 이미 버린 배치다 —
낡은 의도에 대고 의견을 말하게 되고, 그것이 §문제 의 통증이다.
그리고 read-path 가 LLM 을 기다리면 INV-4 가 무너진다.

**인지는 자동, 전달은 버튼.** 물어볼 것이 있을 때만 표시와 버튼이 뜬다 —
캡틴은 무엇을 물어야 할지 모르셔도 된다.

### 어긋남은 감추지 않는다

DB 와 티켓이 갈라지는 것은 이제 필연이다 — 티켓은 크루의 PR 로, 단계는 DB 로 따로 움직인다.
순서를 관리대상 문서에 뒀다면 같은 커밋에 실려 리뷰에서 보였을 텐데 이 구조는 그 안전장치를 안 갖는다.
**대신 읽는 쪽이 큰 소리로 말한다** — `unknown` · `unreadable` · `unclaimed` 을 감추지 않는 것과 같은 원리다.

- **단계 없는 티켓** — 새로 썼는데 계획에 안 넣음
- **티켓 없는 단계** — 티켓이 사라졌거나 번호가 바뀜
- **끝났는데 앞 단계에 남은 것** — §문제 의 넷이 이 표시로 잡혔을 것이다

- **INV-3** — 상태·막힘·완료·처리중은 볼 때마다 다시 읽는다.
- **INV-4** — `next` 와 화면의 즉시 검사는 전부 계산이다. `왜` 는 요약하지 않고 verbatim 릴레이한다.
- 🔴 **판정 자리는 하나뿐** — `next` 계산은 화면과 CLI 가 **같은 함수**를 쓴다.
  둘이 각자 판정하면 그 순간부터 하나는 거짓이다(S2 가 같은 이유로 세운 규율).

  단계·순위가 들어와도 새 정렬 함수를 만들지 않는다.
