# T04 — Plan/Steps tab caching

## Goal
`GET /api/plan/:slug` also benefits from caching, so the `plan` and `steps` tabs render instantly after first load. Previously each request re-runs expensive reads.

## Why this slice
The `plan` and `steps` tabs render from plan/process data that requires reading backlog, features, etc. Each request runs expensive operations. Caching makes the tab responsive.

## Design
- Add `getPlanBoard(slug)` in `app.ts` that caches the plan board response with 5s TTL.
- The response includes board state + steps data.
- `clearDiscoverCache()` flushes this cache on doc changes.
- The `plan` query in `useLiveSync` has its own `staleTime` but this cache sits below it.

## Acceptance criteria
1. `GET /api/plan/:slug` first call: reads plan board data (reads plan.db, features, etc).
2. Second call within 5s: cache hit, instant.
3. Doc change → cache cleared → next request recomputes.
4. `pnpm -C code/web verify` green.

## Verification
- `curl -s http://localhost:8804/api/plan/ticket-01` first call: reads plan data.
- Second call within 5s: <100ms (cache hit).
- `pnpm -C code/web verify` green.

## Sprint note
Consistent with T01/T02/T03 pattern — cache the per-slug response so the plan/steps tab renders instantly after first load. The `openFeatures` count from T01 integrates here if needed, but the primary caching is of the plan board state.
