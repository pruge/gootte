# T04 — git 위치 스탬프: 부팅 직후 백그라운드 재검증

**캡틴 확인:** 필요 없음

## Goal

즉시 서빙된 스냅샷이 **현재 SoT 의 파생물인지를 백그라운드로 확인하고, 다르면 그 프로젝트만
갱신한다.** 스냅샷은 "스캔 시점의 값" 이므로, 이 검증이 INV-3(stale 뷰 금지)를 실제로 지키는
자리다.

## Why this slice

T03 이 부팅을 즉시로 만들면 화면이 잠깐 스캔 시점 내용을 볼 수 있다. 커밋이 밤사이 쌓였다면
그 화면은 stale 이다. 캡틴 지시(2026-08-27): "background 로 git 의 시점을 다시 파악한다.
새로운 git 이 등록되었으면 내용을 갱신하도록 한다." 값의 신선함 판정을 시계(TTL)에서 git
위치 비교로 바꾸는 조각이다(adr/0001 결정 3).

## Produces

**부팅 직후 1회 + watch-fallback 동안 주기적으로 도는 HEAD 재검증 절차.**

- 사본마다 `headCommit(repo)`(`core-io/src/git.ts:69`) — 싼 호출(rev-parse). 사본 수 × 수십 ms.
- 스탬프와 같으면 → 조용히 확정(방송 없음). 다르면:
  - 해당 프로젝트만 재계산(readFeatures) → 메모리 + 디스크 스냅샷 교체 + 스탬프 갱신
    (T03 저장소에 write-through).
  - `ChangeEvent` 방송으로 열려 있는 화면을 고친다(`kind: "project"` — 감시 배선과 같은 언어).
- discover 변화(새 프로젝트·사라진 사본) 발견 시 목록 수준 갱신(`kind: "projects"`).
- watch-fallback 환경(감시 불가)에서는 이 절차가 fallback 주기(15s, T02)의 백업 신선함
  근거가 된다 — 세부 주기·트리거는 구현에서 정하되 기존 폴백 타이머와 새로 자리를 파지 않는다.

## Consumers

- T03 의 스냅샷 모듈 — stamps 읽기·쓰기.
- `backend/src/server.ts` 의 ChangeEvent 방송 배선(기존 hub.broadcast 재사용).
- 프론트엔드 live.ts — kind 단위 invalidate(T02 배선 유지, 새 계약 없음).

## Explicitly out of scope

- 커밋되지 않은 변경(작업 중 md 편집)의 감지 — 그것은 감시기 몫(T05)이다. 스탬프는 커밋 단위
  신선함만 말한다. watch-fallback 환경에서 uncommitted 반영이 늦어지는 것은 알고 있는 한계다.
- 폴백 폴링 정책 바꾸기 — T02 그대로.
- UI 에 "as of ..." 문구 노출 — spec Scope 아님.

## Locked decisions

- 🔴 **방송 없는 무변경 확정** — 같으면 소리 없이 넘어간다. 매번 방송하면 부팅 직후 전 화면이
  이유 없이 깜빡인다(INV-3 은 "stale 하게 두지 마라" 지 "다시 그려라" 가 아니다).
- 검증 자체는 LLM-free, 결정적(INV-4) — rev-parse 결과 문자열 대조뿐이다.
- 순서 보장: 재계산이 끝난 뒤에 스탬프를 새 head 로 찍는다. 먼저 찍으면 그 사이 새 커밋을 놓친다.

## Acceptance criteria

1. 스냅샷 기록 후 커밋을 하나 더 쌓고 재부팅하면, 부팅 직후 화면은 스캔 시점 내용으로 시작해
   검증 완료 후 갱신된다(git 위치가 달랐다는 사실이 화면 변화로 드러난다).
2. 변화가 없으면 부팅 후 어떤 방송·깜빡임도 없다.
3. 격리된 프로젝트 하나만 변했으면 나머지 프로젝트의 재계산이 일어나지 않는다.
4. `pnpm verify` green.
