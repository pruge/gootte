# T03 — Feature cache (slug別)

## Goal
`GET /api/features/:slug` also benefits from caching, so the `features` tab doesn't stall on every request. `readFeatures` per feature slug runs git subprocesses per feature folder.

## Goal
Cache feature reads per slug + copies. When the same slug is requested within TTL, return cached feature docs instead of re-reading git.

## Why this slice
The `features` tab renders per-feature details. Each `GET /api/features/:slug` triggers `readFeatures(copies)` which walks `docs/features/` and runs git subprocesses per feature folder. Caching per slug means the tab renders instantly after first load.

## Design
- Add `getFeatureDocs(slug, copies)` in `core-io/src/features.ts` that caches per `(slug, copies)` with 5s TTL.
- `app.ts` `/api/features/:slug` handler calls `getFeatureDocs` instead of raw `readFeatures`.
- Cache key = `slug + "|" + copies.join(",")`.
- `clearDiscoverCache()` also flushes this cache (same `clearDiscoverCache` function, just a different cache entry).

## Acceptance criteria
1. `GET /api/features/:slug` first call: reads features (git subprocesses, ~1-3s per slug).
2. Second call within 5s: instant (cache hit).
3. After doc change (via watcher) → cache cleared → next request recomputes.
4. `pnpm -C code/web verify` green.

## Verification
- `curl -s http://localhost:8804/api/features/ticket-01` first call: reads features.
- Second call within 5s: <100ms (cache hit).
- `pnpm -C code/web verify` green.

## Sprint note
Consistent with T01/T02 pattern — cache the per-feature result so the `features` tab renders instantly after first load. The `features` tab shows openFeatures count and feature status; this caching makes the tab responsive.
