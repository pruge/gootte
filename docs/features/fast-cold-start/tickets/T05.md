# T05 — 감시 중 증분 write-through: 전부 flush 하지 않고 변경분만 반영

**캡틴 확인:** 필요 없음

## Goal

앱이 켜져 있는 동안 문서 변경이 오면 **해당 프로젝트(슬러그)만** 재계산해 메모리·디스크
스냅샷에 반영한다. 지금은 `onProjectsChange: clearDiscoverCache`(`server.ts:85`)가 전부
flush 해서 다음 요청이 스냅샷 유무와 무관하게 무거운 경로로 빠진다.

## Why this slice

캡틴 지시(2026-08-27): "앱이 켜져 있을 때는 실시간으로 감시한다. 변경된 내용만 추가하여
cache를 업데이트한다." 이벤트 원천은 이미 어느 프로젝트인지 알고 있다 — `core-io/src/watch.ts:121`
이 `{ kind: "project", project: slug }` 로 fire 한다. 그 세세함을 flush 배선이 버리고 있을 뿐이다.

## Produces

**watcher → 캐시 배선의 세분화.**

- `server.ts:85` — flush 배선을 "해당 슬러그의 프로젝트만 재계산해 메모리·디스크에 반영하는
  호출"로 바꾼다(T03 저장소의 update-one API).
- 감시기의 coarse 신호(`kind: "projects"`, watch.ts:174 — 사본 추가/삭제 등)는 discover 수준
  갱신으로 대응한다.
- 방송은 기존 ChangeEvent 언어 그대로 — 프론트엔드 계약 변경 없음.

## Consumers

- T03 스냅샷 모듈(update one project).
- T04 의 검증 절차(같은 write-through 경로를 공유한다).
- `frontend/src/lib/live.ts` — 기존 kind 단위 invalidate(T02) 그대로.

## Explicitly out of scope

- 프론트엔드 새 쿼리 키나 새 무효화 규칙 — 기존 배선이 이미 kind 를 안다.
- 스냅샷 파일의 부분 저장 최적화 — 통째 재직렬화로 충분하면 그렇게 한다.
- watch-fallback 주기 제어 — T04 몫.

## Locked decisions

- 🔴 **재계산은 "마지막 방송" 기준 한 번만** — 같은 프로젝트에 연속 변경이 몰리면 디바운스/
  coalesce 하는 건 구현 판단이되, 요청마다 13초 재계산이 되풀이되는 형태는 안 된다
  (fix/projects-listing-spin 의 재발).
- INV-4 — 변경 반영도 계산이다. 파일 diff 요약 같은 지능을 중간에 넣지 않는다;
  바뀐 것은 해당 슬러그의 md 원문이고, read-path 는 결과를 verbatim 릴레이한다.

## Evidence anchors

- `code/web/backend/src/server.ts:81-86` — onChange/onProjectsChange 배선 (flush ← 고칠 줄)
- `code/web/core-io/src/watch.ts:121` — per-slug fire · `:174` — coarse fire
- `code/web/backend/src/discover-cache.ts` — clearDiscoverCache(전면 flush, 후계될 자리)

## Acceptance criteria

1. 감시 환경에서 특정 프로젝트 문서를 편집하면 그 프로젝트의 데이터만 다시 계산된다
   (다른 프로젝트 git 하위프로세스 0건).
2. 변경 직후 화면이 갱신되며, 폴백 폴링 환경에서도 T02 정책 내에서 반영된다.
3. 연속 변경(coalesce 상황)에서 무한 재계산 큐가 생기지 않는다.
4. `pnpm verify` green.
