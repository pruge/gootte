# 0001 — TTL 폐기 폴백을 버리고 git 스탬프 검증 영구 스냅샷으로

**Status:** accepted (2026-08-27)

## 맥락

`fast-cold-start` 는 첫 두 티켓(T01 · T02)으로 `/api/projects` 를 **5초 TTL 메모리 캐시 + 폴백
폴링 제외**로 멈춰 세웠다(커밋 `2e4c049`, PR #88). 그러나 이 설계는 근본 문제를 안 남긴다:

- 캐시의 생애가 **프로세스와 함께 산다.** 앱을 다시 키면 첫 요청은 언제나 13초 — 콜드 스타트가
  해결된 게 아니라 콜드 스타트가 한 주기당 한 번으로 줄었을 뿐이다.
- TTL 이 만료되면 읽어온 정보를 **버리고 전체를 다시 계산한다.** 13초짜리 재계산은 프로세스가
  살아 있는 동안에도 계속 반복된다.
- 무효화가 "5초 뒤 만료" 와 "watcher 이벤트 → 전부 flush" 뿐이라, 값의 신선함을 **판단하는
  근거가 git 이 아니라 시계**다.

캡틴 지시(2026-08-27, 원문 정리):

> 앱을 실행했을 때 discover한 정보가 없으면 스캔해서 수집한다. 스캔한 정보는 영구히 갖고 있고,
> 스캔 시점의 git 위치를 기록한다. 다음 실행에서는 가진 정보로 바로 띄우고, 백그라운드로 git
> 시점을 다시 파악해 새 커밋이 있으면 갱신한다. 앱이 켜져 있는 동안에는 실시간 감시로 변경된
> 내용만 반영해 cache를 업데이트한다.

## 결정

1. **스냅샷을 디스크에 영구 저장한다.** 위치는 gootte 자기 데이터 디렉터리
   (`GOOTTE_DATA_DIR`, 기본 `~/.gootte`) — 관리대상 프로젝트가 아니므로 INV-2 위반이 아니다.
   스냅샷에 담는 것: discover 결과(슬러그 → 사본 경로), 사본마다 **스캔 시점 git 위치
   (`headCommit`)**, 프로젝트별 `readFeatures` 계산 결과.
2. **부팅 경로를 바꾼다.** 스냅샷이 있으면 첫 `/api/projects` 요청도 즉시(<100ms) 서빙한다.
   스냅샷이 없을 때만 전체 스캔을 돌고, 결과를 곧장 저장한다.
3. **신선함 판정을 시계(TTL)에서 git 으로 바꾼다.** 부팅 직후 백그라운드로 사본마다 현재
   `headCommit` 을 스탬프와 비교한다. 같으면 스냅샷이 현재 SoT 의 파생물임이 확인된 것이고,
   다르면 **그 프로젝트만** 재계산해 스냅샷을 교체하고 ChangeEvent 로 화면을 고친다.
4. **감시 중에는 증분 write-through.** watcher 이벤트가 오면 flush 대신 해당 프로젝트/슬러그만
   재계산하고 메모리·디스크 스냅샷을 동시에 고친다.
5. **TTL 만료 폐기를 빼거나 최후의 안전망으로만 남긴다.** 값을 믿는 근거는 더 이상 "5초 안에
   계산했다" 가 아니라 "git 위치가 같았었다" + "감시가 지금 지키고 있다" 다.

## 불변식과의 정합 (INV-1·2·3·4·5)

- **INV-1 (파생물만):** 스냅샷은 관리대상 md SoT + 격리 사본 관측에서 얼마든지 재생성되는
  파생물이다. 손으로 유지하지 않고, 코드가 쓴다(AUTO-GENERATED 성격). 파일이 깨졌거나 어긋난
  것 같으면 통째로 버리고 재스캔하면 끝이다 — 그래서 desync가 치명적이지 않다.
- **INV-2 (관리대상 읽기 전용):** 쓰는 자리는 gootte 자기 데이터 디렉터리뿐이다. 변함없다.
- **INV-3 (stale 뷰 금지):** 스냅샷 서빙은 화면이 잠깐 스캔 시점 내용을 볼 수 있다. 허용되는
  유일한 stale 폭은 **"부팅 ~ 부팅 후 스탬프 검증 완료"** 이고, 그 사이는 감시 시점 기준
  가장 신선한 걸려 있는 값이다. 검증이 불일치를 찾으면 재계산 후 방송으로 즉시 교체하며,
  앱이 켜져 있는 동안에는 감시기가 변경을 실시간으로 흘린다. stale를 없애는 자리는
  **검증과 감시**이지 스냅샷 폐기 시계가 아니도록 옮긴 것이다.
- **INV-4 (read-path 결정적):** 스냅샷에 저장하는 것은 계산값과 verbatim 릴레이 원문뿐이다.
  요약·추론이 스냅샷에 들어오는 일은 없다. 이 기능이 추가하는 것은 "언제 어떤 입력에서
  계산했는가"(스탬프) 뿐이다.
- **INV-5 (계획만 저장):** 엄밀히 보면 스냅샷은 "원본을 다시 읽으면 같은 값이 나오는" 데이터다.
  하지만 INV-5 가 막으려는 것은 사람이 유지하는 이차 계획·사실이 원장과 어긋나 거짓말을
  하는 것이고, 기계가 쓰고 git 스탬프 하나로 소멸 가능한 memoized 파생물은 INV-1 의
  render-data 소관이다. 이 경계를 여기 명문화한다.

## 대안

- **TTL 인메모리 캐시 유지(현행):** 재시작할 때마다 콜드 스타트가 되살아나 해결이 안 된다. 기각.
- **sqlite/plan.db 안에 스냅샷:** 구조화 데이터로는 매력적이나, 내용이 JSON 직렬화 가능한
  readFeatures 결과라 단일 파일(zod 스키마 검증)로 충분하다. 필요해지는 시점에 결정한다.
- **HEAD 비교를 주기 polling 으로:** 감시기가 살아 있는 환경에서는 file event 가 이미 충분하다.
  HEAD polling 은 감시가 닫힌 환경(watch-fallback)의 백업 수단으로 T04 의 선택지로 남긴다.
