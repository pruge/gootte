# Grill — steps-start-from-dependencies

기능 폴더를 작업 대상에 올리는 순간, 티켓 의존 관계를 읽어 단계를 매긴다.

## 설계 트리

```
자동 단계 배정
├── 언제 도는가                      → D1 (캡틴)
├── 손으로 정한 순서를 덮는가        → D1 (캡틴)
├── 다시 올라올 때 끝난 티켓은       → D2 (캡틴)
├── 의존 관계를 어디서 읽는가        → F1 (사실)
│   └── 두 관례가 충돌하는가         → F2 (사실)
├── 순환 의존은                      → F3 (사실/원칙)
├── 어느 자리에 심는가               → F4 (사실)
├── 저장 형태가 받쳐주는가           → F5 (사실)
└── 지금 동작과 어긋나는 곳은        → F6 (사실)
```

## 라운드 로그

### 1라운드 (2026-08-25)

사관장이 먼저 저장소를 읽어 F1~F6 을 확정했다.
그 결과 처음 다섯 개로 올라왔던 "설계 공백" 중 넷은 캡틴께 여쭐 것이 아니라 **찾으면 나오는 사실**이었다.
캡틴께는 판단이 필요한 두 가지만 올렸다.

| # | 물은 것 | 캡틴이 정하신 것 |
|---|---|---|
| Q1 | 자동 배정이 손으로 정한 순서를 덮는가 | D1 — 덮지 않는다. 등록 시점 1회뿐이다 |
| Q2 | 언제 도는가 | D1 — 작업 대상에 등록할 때 딱 한 번 |
| Q3 | 되올라온 기능의 끝난 티켓은 | D2 — 단계에서 숨긴다 |

프론티어가 비었다.
남은 것은 아래 §열린 정합성 질문 하나이고, 그것은 spec 단계에서 화면으로 확인한 뒤에야 캡틴 질문이 될지 판정된다.

## 캡틴 결정 (원문)

### D1 — 등록할 때 1회 (2026-08-25)

> "자동배정은 feature을 작업 대상에 등록할때 1회 실행된다.
> 그후 내가, 혹은 네가 순서를 조절할수 잇다."

자동 배정은 기능이 **작업 대상 칸에 올라오는 그 순간에만** 돈다.
그 뒤로는 다시 돌지 않는다 — 티켓 의존이 바뀌어도, 새 티켓이 붙어도 재계산하지 않는다.
이후의 순서 조정은 캡틴 손(process 탭 드래그)과 사관장 손(`step` 명령)이 맡고, 자동 배정은 그 위를 덮지 않는다.

🔴 이 결정은 기존 결정과 **충돌하지 않는다.**
"단계는 문서에 있으면 안 되고 db 에 잠시 붙었다 사라진다"(plan-board/spec.md §단계)는 그대로다.
바뀌는 것은 **붙을 때의 초기값**뿐이다 — 지금은 전부 9999, 앞으로는 의존에서 계산한 값.
9999 라는 "아직 순서를 안 정했다" 표현도 살아남는다(의존이 없거나 계산할 수 없는 티켓의 값이다).

### D2 — 되올라온 기능의 끝난 티켓은 숨긴다 (2026-08-25)

> "가령 대기/완료에 있다가 추가로 ticket이 생성되어 다시 작업대상으로 feature가 올라올경우
> steps에는 완료 처리된것은 숨김처리된다."

대기·예약·완료 칸에 있던 기능에 새 티켓이 생겨 다시 작업 대상으로 올라올 때, **이미 끝난 티켓(`done`·`dropped`)에는 단계 행을 만들지 않는다.**
단계 화면에는 남은 일만 선다.

## 사관장이 확정한 사실

### F1 — 신관례 티켓의 의존은 지금 안 읽힌다

`parseNewTicket`(`core/src/parse/feature.ts:332`)은 `num`·`slug`·`path`·`title` 넷만 돌려주고 본문을 버린다.
`tickets/T<NN>.md` 의 `## Depends on` 절은 파서에 닿지 않는다.
따라서 "읽는 코드를 만든다" 는 **해야 할 일**이지 결정할 거리가 아니다.

증거: `tauri-desktop-app/tickets/T01~T05.md` 전부 `## Depends on` 을 갖고 있으나 화면 어디에도 반영되지 않는다.

### F2 — 두 관례는 충돌하지 않는다

옛 관례 `**Blocked by:** 01, 02` 는 이미 파싱되어 `blockedBy` 에 실린다(`core/src/parse/feature.ts:91`).
그 의미는 `docs/agents/issue-tracker.md:38` 이 못박은 대로 **같은 기능 폴더 안 티켓 번호에 대한 구조적 의존**이다.
신관례 `## Depends on` 이 뜻하는 것과 같다.

한 개념의 두 표기다.
파서가 읽는 자리가 하나 늘 뿐, 모델에는 새 개념이 생기지 않는다.

### F3 — 순환은 캡틴 정책이 필요 없다

순환 의존이 있으면 **자동 배정을 거부하고 그 사실을 드러낸다.**
없는 순서를 지어내지 않는다 — INV-4(문서에 없는 것을 그리지 않는다)의 직접적 귀결이다.
거부된 티켓은 9999 로 남아 눈에 띈다.

### F4 — 심는 자리는 이미 하나로 서 있다

`planMove`(`core/src/plan/move.ts:86`)의 `setSteps` 가지가 그 자리다.
지금 코드:

```ts
setSteps: toActive
  ? moved.filter((slug) => !wasActive(slug))
      .flatMap((slug) => (featureOf.get(slug)?.tickets ?? []).map((t) => ({
        feature: slug, ticket: t.slug, step: UNRANKED_STEP,
      })))
  : []
```

이미 "작업 대상에 새로 올라온 기능의 티켓마다 단계를 심는" 동작이고, 심는 값이 전부 9999 일 뿐이다.
자동 배정은 **이 값을 바꾸는 것**이지 새 쓰기 경로를 여는 것이 아니다.
`wasActive` 필터가 이미 있어 D1 의 "1회" 도 그대로 지켜진다 — 작업 대상 안에서 순서만 바꾼 카드는 이 가지에 들어오지 않는다.

### F5 — 저장 형태가 이미 받쳐준다

`step` 칸은 정수가 아니라 **실수**다(plan-board/08, spec §사이에 끼워 넣으려면 저장 숫자가 정수여선 안 된다).
그리고 `computeDisplaySteps`(`core/src/plan/step.ts:63`)가 저장 숫자를 크기순으로 세워 1부터 다시 매겨 보여준다.

따라서 자동 배정이 심는 값은 **연속일 필요가 없다.**
`1, 2, 3` 이든 `1, 5, 9` 든 캡틴 눈에는 똑같이 1단계·2단계·3단계다.

### F6 — 지금 동작 중 D2 와 어긋나는 곳

`planMove` 의 위 코드는 `ticketBoxState` 를 보지 않는다 — **끝난 티켓에도 단계를 심는다.**
그리고 `ProcessView.tsx:412` 는 그 줄을 `[x]` 글리프로 그린다.

D2 는 이 심기 필터를 바꾼다.

## 열린 정합성 질문 (spec 단계에서 판정)

D2 는 **되올라오는 순간**의 심기를 다룬다.
그런데 **이미 작업 대상에 있는 동안** 티켓이 완료되면 그 단계 행은 그대로 남고 화면에 `[x]` 로 계속 보인다(현행, `process.test.ts:60` 이 그 동작을 못박고 있다).

두 경우가 다르게 보이게 된다.

spec 단계에서 화면으로 확인하고 다음 중 하나로 닫는다:
- **좁은 해석(기본값)** — D2 는 심기 시점 필터다. 진행 중 완료된 티켓은 지금처럼 남는다. 그 단계가 전부 채워지면 `computeDisplaySteps` 가 이미 당겨서 걷어낸다.
- **넓은 해석** — 끝난 티켓은 단계 화면에서 일반적으로 사라진다. `process.test.ts:60` 과 `step.test.ts` 의 당김 규칙 여럿을 뒤집는다.

좁은 해석을 기본으로 하되, 화면에서 실제로 어긋나 보이면 그때 캡틴께 올린다.
**지금 캡틴께 여쭐 단계가 아니다** — 화면 증거 없이 묻는 것은 추측을 묻는 것이다.

## 용어

새 용어를 만들지 않는다.
`단계`(step)·`작업 대상`(active)·`미배정`(9999, `UNRANKED_STEP`)은 plan-board/spec.md 가 이미 소유한다.
`의존`은 옛 관례 `Blocked by:` 와 신관례 `Depends on` 두 표기를 같은 개념으로 묶어 부른다.
