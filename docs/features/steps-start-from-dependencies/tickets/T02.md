# T02 — 등록할 때 의존에서 단계를 매긴다
Time: started=2026-08-26T09:35:09+09:00 finished=2026-08-25T20:42:43+09:00

## Goal

기능이 작업 대상에 올라오는 순간, 티켓 의존 관계에서 단계 번호를 계산해 심는다.
지금의 일괄 9999 심기를 대체한다.
되올라온 기능의 끝난 티켓에는 단계를 심지 않는다(D2).

## Why this slice

캡틴 결정 D1·D2 의 본체이자 이 기능의 유일한 사용자 가시 동작이다.
T01 이 입력(의존)을 만들고, 이 티켓이 그것을 단계로 바꿔 화면에 세운다.

## Produces

작업 대상 등록 시 심어지는 **단계 숫자**.
지금은 티켓마다 무조건 `UNRANKED_STEP`(9999)이고, 앞으로는 의존 위상에서 계산한 값이다.
그리고 **끝난 티켓에는 행 자체를 만들지 않는다**는 새 규칙.

## Consumers

심어진 단계 행을 읽는 기존 자리 전부.
이 티켓은 값의 **의미**를 바꾸지 않고 **초기값**만 바꾸므로 아래 자리들은 코드 변경 없이 새 값을 그대로 받아야 한다 — 각 자리가 실제로 그러한지 확인하는 것이 이 티켓의 일이다:

- `core/src/plan/step.ts:63` `computeDisplaySteps` — 저장 숫자를 화면 단계 1..N 으로 압축한다. 심은 값이 연속이 아니어도 옳게 압축되는지 확인한다(F5).
- `core/src/plan/step.ts:120` `placeStep` — 캡틴이 드래그해 놓은 자리를 저장 숫자로 바꾼다. `allNumbered` 를 저장 전부에서 세므로 새 초기값과 부딪치지 않아야 한다.
- `core/src/plan/process.ts:68` `groupProcessSteps` — 단계별로 티켓을 묶는다. 같은 단계에 여럿이 붙는 경우(병렬 티켓)를 이미 다룬다.
- `core/src/plan/next.ts:30` `computeNext` — 다음에 할 일을 고른다. `computeDisplaySteps` 를 거치므로 자동으로 따라온다.
- `core-io/src/plan-store.ts:255~258` — `setSteps` 를 계획 DB 에 쓴다. 기능 단위로 기존 행을 지우고 다시 쓴다.
- `backend/src/app.ts:208` — `/api/plan/:slug` 응답에 표시 단계를 싣는다.
- `backend/src/app.ts:426` — `/step` 라우트가 `placeStep` 을 부른다.
- `cli/src/commands.ts:153` `board` — 표시 단계를 출력한다.
- `cli/src/commands.ts:164` — 9999 를 `"9999"` 문자열로 표시한다. 미배정이 여전히 나올 수 있으므로 그대로 둔다.
- `frontend/src/components/process/ProcessView.tsx:94~95` — 번호 매겨진 묶음과 9999 묶음을 가른다.
- `frontend/src/components/plan/CardDialog.tsx:152` — `9999` 를 `—단계` 로 그린다.
- `core/src/plan/close.ts:122~123` — 단계 행의 **또 다른 쓰기 자리**다(완료로 닫을 때 `clearSteps`, `setSteps: []`). 이 티켓은 여기를 바꾸지 않지만, 단계 쓰기가 `move.ts` 하나뿐이 아님을 알고 있어야 한다 — 아래 Explicitly out of scope 참조.
- `core/src/plan/fixtures.ts` — 테스트 티켓 생성기. T01 이 의존 칸을 더한다. 이 티켓의 배정 테스트가 그 칸을 쓴다.

## Explicitly out of scope

- 의존이 바뀔 때마다의 재계산 — D1 이 명시적으로 배제한다. 이 티켓이 건드리는 것은 등록 시점 하나뿐이다.
- `placeStep`·process 탭 드래그·`step` 명령의 동작 — 손대지 않는다.
- `computeDisplaySteps` 의 당김 규칙 — 손대지 않는다.
- 이미 작업 대상에 올라와 있는 기능의 기존 단계 값 — 소급 적용하지 않는다.
- `core/src/plan/close.ts:122~123` 의 단계 쓰기 — 완료로 닫을 때 단계 행을 지우는 경로다. 등록 시점이 아니므로 D1 의 범위 밖이고, 손대지 않는다. 여기 적어 두는 이유는 그 부재가 **빠뜨림이 아니라 결정**으로 읽히게 하기 위해서다.
- 진행 중 완료된 티켓의 단계 행 처리 — `spec.md` §열린 정합성 질문 참조. **좁은 해석을 따른다**: 이 티켓은 심기 시점만 필터하고 진행 중 완료는 현행대로 둔다.

## Locked decisions

- **D1**(`grill.md`): 등록 시 1회. `planMove` 의 `wasActive` 필터가 이미 이것을 보장하므로 **그 필터를 유지한다**. 작업 대상 안에서 순서만 바꾼 카드는 이 가지에 들어오지 않는다.
- **D2**(`grill.md`): 되올라올 때 `done`·`dropped` 티켓은 단계 행을 받지 않는다.
- **F3**(`grill.md`): 순환 의존이면 그 티켓들의 자동 배정을 **거부하고 9999 로 남긴다**. 순서를 지어내지 않는다. 순환에 걸리지 않은 나머지 티켓의 배정은 계속된다.
- **F5**(`grill.md`): 저장 숫자는 실수이고 화면이 압축하므로 **연속일 필요가 없다**. 촘촘하게 만들려고 애쓰지 마라.
- 9999 는 계속 "아직 순서를 안 정했다"의 **유일한** 표현이다(`plan/move.ts:11` 주석). 그 뜻의 두 번째 표현을 만들지 마라.
- `move.test.ts` 의 두 테스트가 못박은 **"심는다"와 "옛 숫자를 되살리지 않는다"는 규율은 유지**된다. 바뀌는 것은 심는 값뿐이다. 테스트를 지우지 말고 새 기대값으로 갱신하라.

## Implementation notes

배정 규칙은 위상 정렬이다 — 선행이 없으면 1단계, 있으면 모든 선행의 최대 단계 + 1.
서로 독립인 티켓은 자연히 같은 단계를 공유한다(사용자 스토리 2·3).

배정할 수 없는 티켓은 9999 로 남긴다:
- 순환에 걸린 티켓
- 존재하지 않는 번호를 가리키는 티켓
- 의존 절이 없어 관계를 모르는 티켓

계산은 순수 함수여야 한다 — 입력은 티켓 목록, 출력은 티켓별 단계 번호.
파일 읽기도 DB 접근도 하지 않는다(`core` 계층 경계).

## Acceptance criteria

1. 의존 없는 티켓만 있는 기능을 올리면 전부 1단계에 붙는다.
2. `T01 → T02 → T03` 선형 의존이면 각각 1·2·3단계에 붙는다.
3. `T01` 뒤에 `T02`·`T03` 이 나란히 오면 둘 다 2단계를 공유한다.
4. 순환에 걸린 티켓은 9999 로 남고, 나머지는 정상 배정된다.
5. 존재하지 않는 번호를 가리키는 티켓은 9999 로 남는다.
6. 작업 대상 안에서 순서만 바꾼 카드의 단계는 재계산되지 않는다.
7. 되올라온 기능의 `done`·`dropped` 티켓에는 단계 행이 없다.
8. 화면 표시 단계가 1부터 연속으로 보인다(저장 숫자가 성겨도).
9. 위 Regression guards 전부 green.
