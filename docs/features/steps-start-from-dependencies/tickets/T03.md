# T03 — T-review: 사관장 검수
Status: resolved (2026-08-25)

## Goal

캡틴이 앱을 띄워 spec 수용기준대로 자동 단계 배정을 확인한다.

## Why this slice

말단 검수 티켓은 모든 승인된 티켓 그래프의 필수 종착점이다.
계획판 핵심 모델의 초기값을 바꾸는 변경이라 실물 확인 없이 닫지 않는다.

## Produces

수용 판정.
코드 변경이 필요하면 그 결과로 나오는 후속 작업.

## Consumers

- `docs/features/steps-start-from-dependencies/spec.md` §Acceptance criteria — 검수 기준의 단일 출처
- `docs/features/plan-board/spec.md` §올라온 카드는 9999 단계로 붙는다 — T02 가 이 문서를 갱신했는지 확인한다. 문서와 코드가 어긋나면 그것이 검수 지적이다.

## Touched surfaces

없음 — 검수 티켓은 코드를 만들지 않는다.
검수 중 나온 지적의 수정은 별도 후속 작업으로 뺀다.

## Explicitly out of scope

- 실시간 대화형 검수 루프. 캡틴 지시 2026-08-25로 **개발 완료 후 검수** 방식이다. 작업자가 옆에서 대기하며 한 마디씩 받는 형태가 아니다.
- 검수 중 발견된 새 기능 요청의 구현.

## Locked decisions

- 캡틴 지시 2026-08-25: 검수는 개발이 끝난 뒤에 한다. 작업자를 대기시키지 않는다.
- `spec.md` §열린 정합성 질문: 진행 중 완료된 티켓이 단계 화면에 남는 현행 동작은 T02 에서 좁은 해석으로 유지된다. 검수에서 그것이 실제로 어색해 보이면 그때가 캡틴 질문의 시점이다.

## Evidence anchors

- `docs/features/steps-start-from-dependencies/spec.md` §Acceptance criteria 1~8
- `docs/features/steps-start-from-dependencies/grill.md` §캡틴 결정 D1·D2

## Regression guards

T01·T02 가 남긴 테스트 전부가 green 인 상태에서 검수에 들어간다.

## Acceptance criteria

캡틴이 다음을 실물로 확인한다:

1. 의존 없는 티켓만 있는 기능을 올리면 전부 1단계에 붙는다.
2. 선형 의존이면 순서대로 단계가 올라간다.
3. 병렬 가능한 티켓은 같은 단계를 공유한다.
4. 배정할 수 없는 티켓은 9999(—단계)로 남아 눈에 띈다.
5. 손으로 순서를 조정한 뒤 자동 배정이 그것을 덮지 않는다.
6. 되올라온 기능의 끝난 티켓이 단계 화면에 없다.
