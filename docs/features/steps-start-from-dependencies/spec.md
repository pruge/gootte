# Specification — steps-start-from-dependencies

## Goal

기능을 작업 대상에 올리는 순간, 그 기능 티켓들의 의존 관계를 읽어 단계를 매긴다.
지금은 전부 9999(미배정)로 붙고 사관장이 손으로 번호를 매겨야 한다.

## User stories

1. 캡틴이 기능 카드를 작업 대상으로 올리면, 그 기능의 티켓들이 의존 순서대로 1·2·3단계에 붙어 있다.
2. 서로 독립적인 티켓 둘은 같은 단계에 나란히 붙는다 — 병렬로 갈 수 있다는 뜻이 화면에 그대로 보인다.
3. 의존 대상이 없는 티켓은 1단계에 붙는다.
4. 의존 관계를 알 수 없는 티켓(순환에 걸렸거나, 존재하지 않는 번호를 가리키거나, 의존 절이 없는 옛 문서)은 9999 에 남아 눈에 띈다.
5. 캡틴이나 사관장이 그 뒤 순서를 조정하면 그 값이 최종이다 — 자동 배정이 다시 돌아 덮는 일이 없다.
6. 대기·예약·완료 칸에 있던 기능에 새 티켓이 붙어 다시 올라오면, 이미 끝난 티켓은 단계 화면에 서지 않고 남은 일만 보인다.
7. 신관례(`tickets/T<NN>.md`)와 옛 관례(`issues/NN-*.md`) 어느 쪽 폴더든 같은 규칙으로 배정된다.

## Scope

- 신관례 티켓 문서의 의존 절을 읽는 파서
- 티켓 목록 + 의존 관계 → 단계 번호를 정하는 순수 계산
- 작업 대상 등록 시 그 계산 결과를 심기 (지금의 일괄 9999 대체)
- 끝난 티켓을 심기에서 제외 (D2)

## Out of scope

- 의존이 바뀔 때마다의 재계산 — D1 이 명시적으로 배제한다
- process 탭 드래그·`step` 명령의 동작 변경 — 그대로 둔다
- 기능과 기능 사이의 의존 — 단계는 기능 안의 개념이다
- 옛 관례 `Blocked by:` 파서 변경 — 이미 동작한다
- 화면(process 탭·plan 탭) 표시 규칙 변경 — 저장 숫자만 바뀌고 표시 계산은 그대로다

## Decisions

D1·D2 는 `grill.md` 가 단일 출처다.
요약: 등록 시 1회만 실행하고 이후 손댄 값을 덮지 않는다(D1) · 되올라올 때 끝난 티켓은 단계에서 제외한다(D2).

사실 F1~F6 도 `grill.md` 참조.
핵심: 신관례 의존은 아직 안 읽히고(F1), 두 관례는 같은 개념이며(F2), 순환은 거부하고 드러내고(F3), 심는 자리는 `planMove` 의 `setSteps` 하나이며(F4), 저장 숫자가 실수라 연속일 필요가 없다(F5).

## Existing seams / integration points

- 의존 읽기: 옛 관례는 이미 `blockedBy` 로 파싱된다. 신관례 파서가 같은 칸을 채우면 하류가 통째로 재사용된다.
- 심기: 작업 대상 등록의 단계 심기 가지가 이미 있다. 심는 값만 바뀐다.
- 표시: 저장 숫자를 화면 단계로 압축하는 계산이 이미 하나로 서 있다. 손대지 않는다.
- 미배정 표현: 9999 는 계속 "아직 순서를 안 정했다"의 유일한 표현으로 남는다.

## Data and migration

스키마 변경 없음 — `step` 칸은 이미 실수를 받는다.
기존 계획 DB 의 값은 손대지 않는다. 새 규칙은 **이후 등록되는 기능**부터 적용된다.
이미 작업 대상에 올라와 있는 기능은 지금 값을 그대로 유지한다(D1 의 "덮지 않는다"가 여기에도 적용된다).

## Security / authorization

없음 — 관리대상 문서는 계속 읽기만 하고, 쓰기는 gootte 자기 계획 저장소에만 일어난다.

## Compatibility / rollout

옛 관례만 쓰는 기능의 동작이 바뀐다 — 지금은 전부 9999 였으나 앞으로는 `Blocked by:` 를 읽어 배정된다.
이것은 의도된 개선이며 캡틴 결정 D1 의 범위 안이다.
의존 절이 아예 없는 티켓만 모인 기능은 전부 1단계에 붙는다(전부 독립이므로 옳다).

## Acceptance criteria

1. 신관례 티켓의 의존 절이 파싱되어 계약의 의존 칸에 실린다.
2. 의존 없는 티켓은 1단계, 의존이 있으면 선행보다 뒤 단계에 붙는다.
3. 서로 독립인 티켓은 같은 단계를 공유한다.
4. 순환에 걸린 티켓은 배정되지 않고 9999 로 남으며, 나머지 티켓의 배정은 계속된다.
5. 존재하지 않는 번호를 가리키는 의존은 배정을 막고 그 티켓을 9999 에 남긴다.
6. 작업 대상 안에서 순서만 바꾼 카드의 단계는 재계산되지 않는다.
7. 되올라온 기능의 `done`·`dropped` 티켓에는 단계 행이 만들어지지 않는다.
8. 기존 vitest 전부 green — 단, 아래 두 테스트는 새 동작에 맞게 갱신된다.

## Verification strategy

위험도 elevated — 계획판 핵심 모델의 초기값을 바꾼다.
vitest(파서·배정 계산·심기 경로) + 기존 회귀 + 앱 실측(기능 하나를 올려 단계가 붙는지 확인).

**갱신이 필요한 기존 테스트 2개**(`core/src/plan/move.test.ts`):
- `🔴 작업 대상으로 올라오면 그 기능 티켓 전부가 9999 단계로 붙는다`
- `🔴 되올린 카드도 9999 에서 다시 시작한다 — 옛 숫자를 되살리지 않는다`

두 테스트가 못박은 것은 "심는다" 이고, 바뀌는 것은 "무엇을 심는가" 다.
"옛 숫자를 되살리지 않는다"는 규율은 그대로 유지되어야 한다 — 새로 계산할 뿐 이전 값을 복원하지 않는다.

## T-review

말단 검수 티켓 필수.
캡틴이 앱을 띄워 기능을 작업 대상에 올려보고 단계가 의존대로 붙는지 확인한다.
개발 완료 후 검수 방식(캡틴 지시 2026-08-25) — 실시간 왕복 루프가 아니다.
