# read-path-redesign — 읽기와 감시를 목적에서 다시 세운다

Status: draft (2026-09-04)

## 캡틴 지시 (원문)

> **"일단 기본적인 구조부터 다시 설계를 하는 게 맞는 것 같아. 지금 기능을 하나하나 하나씩
> 추가하다 보니까 그게 최적화된 구조가 아니라서 문제가 생기는 것 같아. 명백한 목적을 추리고
> 그 목적에 맞게 깔끔하게 최적화된 감시 체계를 갖추고 문서를 읽기를 분류해 나가는 기본적인
> 구조를 다시 잡아줘. 처음부터 다시 설계한다는 개념으로 이해를 하고 잡아줬으면 좋겠어.
> 최종적으로 지금 있는 구조에서 내가 무엇을 기능을 쓰고 있는지를 파악해서 그런 부분을
> 문서화하고 진행했으면 좋겠어."**

발단은 실사용 증상이다:

> **"문서를 클릭하면은 문서를 화면에 표시하기까지 한참 걸려. 그게 한 십몇초까지 돼가지고"**
> **"나는 문서라는 게 바로 클릭하면 읽혀야 된다고 생각하는데"**

## 이 문서가 하는 일

1. **목적을 추린다** — 이 제품이 화면에서 실제로 답하는 질문만 남긴다.
2. **인벤토리를 박제한다** — 지금 화면이 **실제로 소비하는 값**과, 계산되지만 **아무도 안 보는 값**.
3. **읽기를 등급으로 분류한다** — 값마다 입력·비용·필요한 신선도가 다르다. 지금은 그것이 한 덩어리다.
4. **감시 체계를 하나의 축으로 다시 세운다** — 지금은 트리거가 다섯 개 겹쳐 있다.

🔴 이 문서는 **성능 튜닝 문서가 아니다.** 느린 것은 증상이고, 원인은 "무엇을 언제 다시 읽는가"를
기능마다 따로 정한 것이다. 그래서 목적 → 인벤토리 → 등급 → 감시 순서로 간다.

## 1. 목적 — 화면이 답하는 질문은 넷뿐이다

AGENTS.md 머리말이 이미 말한다: **"다음 무엇 / 지금 누가"**. 실제 탭은 넷이다
(`frontend/src/components/main/Tabs.tsx`).

| 탭 | 답하는 질문 | 입력의 출처 |
|---|---|---|
| `memo` | 내가 적어 둔 것 | **gootte 자기 DB만** (관리대상 안 읽음) |
| `features` | 이 프로젝트에 무슨 일이 있고 뭐가 남았나 | 관리대상 문서 + git + 계획 DB |
| `plan` | 무엇부터 할 것인가 (다섯 칸 판) | 관리대상 문서 + 계획 DB |
| `steps` | 지금 무엇을 붙들고, 시간은 어떻게 흘렀나 | 관리대상 문서(`Time:`) + 계획 DB |
| (드로어) | **이 문서 한 장의 원문** | 관리대상 파일 1개 |

🔴 **다섯 번째 줄이 나머지 넷과 성격이 완전히 다르다.** 원문 한 장 읽기는 파일 하나를 여는 일이고,
나머지 넷은 프로젝트 전체를 훑어 만든 파생물이다. **지금 구조는 이 둘을 같은 줄에 세운다** —
그것이 증상의 원인이다.

## 3. 실측 — 무엇이 시간을 먹는가 (jinwooauto · 사본 4개 · 기능 61 · 티켓 238)

| 하는 일 | 시간 |
|---|---|
| `readFeatureDoc` — **드로어가 실제로 하는 일** | **1ms** (20회 반복 4ms) |
| `readFeatures` — 기능/티켓 파생물 전체 재계산 | **5,382ms** |
| `scanWorkingCopies` — 사본 관측 | 1,324ms |
| `sameStamps` — 15초마다 도는 "변했나" 확인 | 1,105ms |

### 🔴 정정 — 비용의 정체는 파일 읽기가 아니라 **git 하위프로세스 개수**다 (2026-09-04 재측정)

처음 이 문서는 22MB 파일 읽기를 원인으로 지목했다. **틀렸다.** 두 가지 측정 실수였다:
(a) git 호출 시간을 PATH 셸 shim 으로 쟀는데 그 shim 이 호출마다 python 을 두 번 띄워
per-call 비용을 ~7배 부풀렸고, (b) 그래서 남는 시간을 파일 읽기로 돌렸다.

직접 재니 이렇다(jinwooauto · 사본 3개 · `npx tsx` 환경):

| 항목 | 실측 |
|---|---|
| 문서 파일 **전부** 읽기 (1,058개 · 12.4MB) | **299ms** |
| 그중 `.md` 만 (1,028개 · 5.5MB) | 136ms |
| **git 하위프로세스 35회** | **≈ 2,800ms** |
| 나머지(파싱·병합·조립) | ≈ 900ms |
| **`readFeatures` 합계** | **≈ 4,000ms** |

🔴 **git 호출 하나가 80ms 인데, 그중 git 이 실제로 하는 일은 거의 없다.**

| 무엇을 쟀나 | 시간 |
|---|---|
| 셸에서 `git --version` ×10 | **12ms/회** |
| plain node 에서 `execFileSync("/bin/echo")` | 3ms/회 |
| plain node 에서 `execFileSync("git", ["--version"])` | **25ms/회** |
| **`npx tsx` 아래에서 같은 호출** | **80ms/회** |

### 🔴 재정정 — 위 표의 "80ms" 는 **내 벤치 하네스(`npx`)의 현상**이었다 (T09, 2026-09-04)

T09 가 원인을 팠더니 `tsx` 가 아니라 **`npx`** 였다:

| 하네스 | `git --version` |
|---|---|
| plain node | 9.3ms |
| **`node --import tsx`** (로더만) | **9.2ms** |
| `pnpm run <script>` (**실제 dev 경로**) | **9.7ms** |
| `npx tsx` (내가 벤치에 쓴 것) | **79.9ms** |

`npx tsx` 아래에서도 **절대 경로**(`/opt/homebrew/bin/git`)로 부르면 9.5ms 다 — 즉 `npx` 가 앞에
붙이는 PATH 를 타고 bare `git` 을 찾는 값이었다. **dev 서버는 `pnpm` 으로 도므로 이 배수가 없다.**

🔴 **그래서 위 표의 절대 수치(35회 ≈ 2,800ms · 합계 4,000ms)는 전부 ~8배 부풀려져 있었다.**
같은 하네스로 앞뒤를 쟀으므로 **상대 개선은 유효**하지만, 절대값은 아래 §3.1 이 SoT 다.

## 3.1 정직한 실측 (현실 하네스 `node --import tsx`, jinwooauto · 사본 3)

| | 1회차(콜드) | 2회차 | 3회차 |
|---|---|---|---|
| **원래 HEAD** | 674ms | 666ms | 633ms |
| **T01~T06 적용 후** | **479ms** | **47ms** | **49ms** |

- 콜드(프로세스 첫 계산): 674ms → **479ms** (−29%)
- **웜(문서가 안 바뀐 재조회): 666ms → 47ms (14배)** ← T04 폴더 단위 캐시의 몫
- git 호출: **35회 → 17회**

원래는 "볼 때마다 매번 666ms" 였다. 지금은 **바뀐 폴더가 없으면 47ms**, 있으면 그 폴더만.

즉 비용은 git 의 작업량이 아니라 **git 바이너리를 띄우는 것 자체**이고, **호출 개수에 선형인 것은
그대로다** — T06 이 그 개수를 줄인 것이 유효한 이유다.

**그래서 지렛대의 순서가 바뀐다:**

1. **git 호출 개수를 줄이는 것**(T06)이 압도적 1위다 — 35회 × 80ms 가 비용의 ~70% 다.
2. **파싱·조립**(T04 의 폴더 단위 캐시가 없앤다) ≈ 900ms.
3. **파일 읽기**(T02)는 `.md` 로 좁혀도 **163ms** 절감이다 — 작다. 여전히 옳은 정리지만 성능
   근거로 팔지 마라.

이 저장소는 이 수치를 이미 한 번 기록했다 — `backend/src/discover-cache.ts:53`:
*"요청 하나가 ~13초가 되고, 감시 폴백 폴링이 그것을 5초마다 다시 돌려 스피너가 멈추지 않는다"*.

## 4. 왜 1ms 짜리 일이 십몇 초가 되나 — 두 겹의 원인

### 원인 A — 전부 동기라 이벤트 루프가 통째로 멈춘다

`readFeatures`·`scanWorkingCopies`·`sameStamps` 전부 `execFileSync`/`readFileSync` 다. Node 는 한
스레드고 Hono 핸들러도 그 위에서 돈다. **`readFeatures` 가 도는 5~13초 동안 드로어 요청은 소켓
큐에서 파싱조차 되지 않는다.** 드로어 경로 자체를 아무리 빠르게 해도 소용이 없다.

### 원인 B — 재계산의 단위가 "프로젝트 전체" 다

문서 **한 장**이 바뀌어도, 기능 **하나**가 새로 생겨도, 61개 기능 × 4개 사본 × 22MB 를 다시 읽는다.
INV-3(stale 뷰 금지)을 **"볼 때마다 전부 다시 계산"** 으로 구현한 결과다.

### 지금까지의 최적화는 캐시 4겹이다 — 빈도만 줄이고 비용은 그대로

| 겹 | 자리 | TTL |
|---|---|---|
| discover 목록 | `discover-cache.ts` `getProjects` | 5초 |
| `/api/projects` 전체 응답 | `discover-cache.ts` `payloadCache` | 5초 |
| 처리중 관측 | `app.ts` `inProgressMem` | 5초 |
| 기능/티켓 파생물 | 디스크 스냅샷 `plan.db` | 영구 |

**hit 이면 빠르고 miss 면 예전 그대로** — 캡틴이 겪는 "가끔 엄청 느림" 의 정체다.
그리고 캡틴이 짚은 두 경우가 정확히 miss 하는 두 경우다:

| 증상 | 코드 자리 | 왜 |
|---|---|---|
| **앱 켜고 처음** | `server.ts:138` `setImmediate(snapshotRevalidator.run)` | listen **직후** 전 프로젝트 풀스윕이 동기로 돈다. 창은 떴는데 백엔드는 잠겨 있다 |
| **처음 새로 잡힌 문서** | `app.ts` `featuresFor` 의 `sameFeatureFolders` | 스냅샷에 없는 기능 폴더를 보면 스냅샷을 **우회하고 그 요청 자리에서** 풀스캔 |

거기에 하나 더: 워크트리에서 **누가 작업 중이면** `hasTrackedUncommittedChange` 가 참이 되어
`sameStamps` 가 매번 거짓 → **15초마다 5.4초짜리 풀 재계산**. 이 대시보드가 제일 쓸모 있는 순간에
제일 느려진다.

## 5. 재설계 ① — 읽기를 네 등급으로 가른다

값마다 **입력·비용·필요한 신선도**가 다르다. 지금은 그 넷이 한 덩어리(`readFeatures`)로 묶여
가장 비싼 것에 전부가 맞춰져 있다. 가르는 기준은 **"무엇이 바뀌면 이 값이 바뀌나"** 하나다.

| 등급 | 값 | 입력 | 무효화 신호 | 필요한 신선도 | 지금 비용 |
|---|---|---|---|---|---|
| **A. 원문** | 문서 한 장의 본문 | 파일 1개 | 없음(항상 디스크) | **즉시** | 1ms |
| **B. 문서 파생물** | 티켓 제목·상태·`Time:`·`blockedBy`·`waitingOn`·문서 트리 | 기능 폴더의 **`.md` 본문** | 그 폴더의 파일 변경 | 수 초 | 5.4초의 절반 |
| **C. 저장소 상태** | 미착지 표식·추적 제외·사본 합집합·갈라짐(`conflict`) | git | HEAD 변경 · 워킹트리 변경 | **십 초대로 충분** | git 71회 |
| **D. 관측** | 미해소 구역 숫자 3개 (`workedBy` 는 미사용) | 사본의 branch·touched | 사본 구성/가지 변경 | 십 초대 | 1.3초 |

### 등급이 정하는 규칙

- 🔴 **A 는 어떤 계산에도 줄 서지 않는다.** 드로어 요청은 B·C·D 를 **한 글자도** 건드리지 않는다.
  지금은 `withWorktrees(proj.copies)` 를 지나 같은 스레드에 서 있다.
- 🔴 **B 의 단위는 기능 폴더다.** 한 폴더가 바뀌면 그 폴더만 다시 읽는다. 프로젝트 전체가 아니다.
- 🔴 **C 는 주기로 갱신하지 않는다 — 이벤트로만 갱신한다**(캡틴 질문 2026-09-04, §5.1).
  못 얻으면 표식을 생략한다 — 지금도 git 이 답하지 않으면 표식 없이 보여주는 규율이 있다(`features.ts` AC6).
- 🔴 **D 는 쓰는 것만 남긴다.** `workedBy` 를 되살릴지, 관측 자체를 진단 요약으로 축소할지는 결정 사항이다.
- 🔴 **B·C·D 는 요청 스레드에서 계산하지 않는다.** 캐시가 비어도 요청은 즉시 마지막 값을 받고,
  계산은 따로 돌아 끝나면 WS 로 밀어 교체한다. 지금 구조가 이미 이 모양을 **의도**했지만
  (`fast-cold-start` T03/T07), 계산이 같은 이벤트 루프에 있어 의도가 성립하지 않는다.

### 5.1 🔴 캡틴 질문 — "모든 문서가 시간을 기록하면 git 감시가 필요한가"

> **"앞으로 모든 문서를 시간을 기록하고 사용할텐데, 그때도 git 감시가 필요할까?"** (2026-09-04)

**답: 주기적 git 감시는 필요 없다. 이벤트로만 물으면 된다.**

먼저 **`Time:` 이 대체하는 것은 이미 대체돼 있다.** 티켓의 상태·시각은 `Time:` 줄을 **사본 전체에서
정방향 병합**해 만들고(`core-io/src/features.ts:295` `mergeTicketTimes`, T05), 이것은 git 의 "어느
사본이 나중 판인가" 판정(`resolveFile`)과 **별개로** 돈다. 처리중 판정도 가지 관측을 버리고
`started=` 로 옮겼다(ADR-0001). **티켓 축에서 git 은 이미 빠져 있다.**

그럼 git 이 남아서 답하는 것은 셋이고, 셋 다 **시간이 지나면 변하는 값이 아니라 무언가가 바뀌면
변하는 값**이다 — 그래서 주기 폴링이 아니라 이벤트가 맞다.

| git 이 답하는 것 | `Time:` 이 대체하나 | 실태와 처분 |
|---|---|---|
| **미착지** `unlanded` | ✗ 다른 질문 | 🔴 **화면에 없다**(§2). **버린다** — 사본마다 도는 `git status`(측정 22회 2.2초)가 통째로 사라진다 |
| **갈라짐** `conflict` | 티켓은 ✓ 이미 대체됨 / 본문은 ✗ | `Time:` 은 git 없이 병합된다. 남는 것은 **`Time:` 줄이 없는 문서**(`spec.md`·`adr/`)의 본문이 사본마다 **바이트로 다를 때**뿐이다 → 폴링이 아니라 **문서를 읽는 도중 조건부**로 묻는다 |
| **추적 제외** `check-ignore` | ✗ `.gitignore` 를 봐야 안다 | 살아 있다(`design/*.html` 을 트리에서 숨긴다). 다만 **`.gitignore` 가 바뀔 때만** 바뀐다 → 그 파일 변경 이벤트로 충분 |
| (`isRepo`) | — | 사본 구성이 바뀔 때만 |

측정한 git 71회의 대부분이 **죽은 값(미착지)이거나 내용 조건부(갈라짐)** 다. 15초 주기 축은 지킬
것이 없어진다. 🔴 **이것이 §6 의 축을 셋에서 둘로 줄인다.**

|---|---|
| 드로어 본문 | A |
| `title` `num` `path` `status` `statusKnown` `sourceStatus` `startable` `waitingOn` `completedAt` `startedAt` `finishedAt` `pauses` `elapsed` `docs`(트리) | B |

### 목표: 축은 둘이다

**축 1 — 파일 감시(이벤트).** 관리대상 **모든 사본**(discover 사본 + Claude Code worktree +
BB worktree)의 `docs/features/**`. 이벤트가 오면 **그 기능 폴더 한 칸만** 무효화한다.
지금 감시는 discover 사본만 보고 worktree 를 안 봐서(`watch.ts` `contentPaths`), worktree 의
untracked 새 티켓은 커밋되기 전까지 어느 경로로도 안 잡힌다.

**축 2 — 사본 구성 · `.gitignore`(이벤트).** C 등급 중 살아남는 것(추적 제외·`isRepo`)은
**드물게, 특정 파일이 바뀔 때만** 변한다. 갈라짐(`conflict`)은 축이 아니라 **B 를 읽는 도중
사본 내용이 실제로 다를 때만** 묻는 조건부 질의다.

🔴 **주기 폴링 축은 없앤다.** 지금 그 자리(15초 `sameStamps`)는 HEAD 확인과 문서 무효화를 **겸해서**,
누가 작업 중이면 문서가 안 바뀌었는데도 문서 파생물을 통째로 다시 만든다. 주기 타이머는 **파일
감시가 아예 안 붙는 환경의 안전망**으로만 남고, 그때도 무효화 단위는 기능 폴더다.

축이 둘로 갈리면 부팅 스윕(1)과 새 폴더 우회(4)는 **축 1 의 특수 경우**가 되어 사라진다 —
부팅 때는 감시기가 초기 스캔으로 전 폴더를 한 번 훑고, 새 폴더는 `add` 이벤트로 잡힌다.

## 8. 하지 않는 것

- **INV 를 고치지 않는다.** INV-1(파생물만)·INV-2(읽기 전용)·INV-3(stale 뷰 금지)·INV-4(결정적)는
  그대로다. 바뀌는 것은 **파생물을 언제 어느 단위로 다시 만드는가**뿐이다.
- **관리대상에 쓰지 않는다.** 캐시·색인은 전부 gootte 자기 저장소(`GOOTTE_DATA_DIR`) 안이다.
- **화면을 바꾸지 않는다.** 이 기능은 같은 화면을 같은 값으로 그리되 기다리지 않게 하는 것이다.
- **stale 을 허용하지 않는다.** "마지막 값을 즉시 주고 준비되면 교체" 는 이미 이 저장소가 고른
  방식이다(adr/0001, `fast-cold-start`). 그것을 **실제로 성립하게** 만드는 것이 이 기능이다.
