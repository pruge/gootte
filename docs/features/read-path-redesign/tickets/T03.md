# T03 — 사이드바 배지가 전 프로젝트 풀스캔을 부르지 않는다

**Blocked by:** 없음 — 즉시 착수 가능

**Time:** started=2026-09-04T11:41:06+09:00 finished=2026-09-04T11:46:58+09:00

## Goal

`/api/projects` 가 사이드바의 남은 티켓 수(`openFeatures`) 하나 때문에 **모든 프로젝트**의
`readFeatures` 를 부르는 구조를 끊는다. 선택된 프로젝트는 즉시, 나머지는 늦게 채운다.

## Why this slice

`/api/projects` 는 첫 화면이 반드시 부르는 라우트다. 프로젝트가 셋인 지금도 그 안에서
jinwooauto 하나가 5.4초를 먹고, 그동안 이벤트 루프가 멈춰 **드로어 클릭이 그 뒤에 선다.**
프로젝트가 늘수록 선형으로 나빠진다. 배지 하나가 첫 화면 전체를 볼모로 잡고 있다.

## Produces

`openFeatures` 가 **선택된 프로젝트만 즉시** 채워진 프로젝트 목록. 나머지는 값이 준비되면
WS(`kind:"project"`)로 밀려 화면이 채운다.

## Consumers

없음(화면이 최종 소비처).

## Touched surfaces

`backend/src/app.ts` (`/api/projects`) · `backend/src/discover-cache.ts` (`payloadCache`) ·
`frontend/src/components/sidebar/Sidebar.tsx` · `contract/src/index.ts`(배지 미정 표현이 필요하면)

## Explicitly out of scope

- 배지를 **없애지 않는다**(캡틴 D3 — 늦게라도 채운다).
- 배지의 계산 규칙(`countOpenFeatures`·백로그 조인) 변경 — 같은 판정 자리를 그대로 쓴다.

## Locked decisions

- **D3** — 선택된 프로젝트만 즉시, 나머지는 백그라운드로 늦게(캡틴, 2026-09-04).

## Evidence anchors

- `backend/src/app.ts:485-503` — `getProjects(...).map` 안에서 프로젝트마다 `featuresFor` 를 부른다.
- `backend/src/discover-cache.ts:53` — *"뿌리가 늘어나면 요청 하나가 ~13초"* 라고 이미 기록돼 있다.

## Regression guards

- 🔴 **배지 숫자가 준비된 뒤에는 지금과 같은 값**이어야 한다 — 백로그 조인을 거친 `countOpenFeatures` 그대로.
- 🔴 **"모름" 을 0 으로 그리지 않는다.** 아직 안 센 프로젝트의 배지는 **비워 둔다** — 0 은 "다 끝났다"
  는 거짓말이다(INV-U1 과 같은 규율: 거짓 값보다 표시 없음이 낫다).
- 🔴 프로젝트 목록 자체(slug·path)는 지금처럼 즉시 온다.

## Scope

1. `/api/projects` 가 배지를 위해 전 프로젝트 `featuresFor` 를 부르지 않게 한다.
2. 선택된 프로젝트의 배지는 즉시 낸다(그 프로젝트는 어차피 `/api/features/:slug` 로 읽힌다).
3. 나머지는 준비되는 대로 채우고 `kind:"project"` 로 알린다.
4. 화면은 **미정 상태**를 0 이 아닌 것으로 그린다.

## Implementation notes

- "선택된 프로젝트" 를 서버가 알아야 하는지, 아니면 화면이 그 프로젝트만 따로 묻는지는 구현 판단이다 —
  후자가 더 단순하면 그쪽을 골라라(서버가 세션 상태를 갖지 않는 쪽이 이 저장소 결에 맞다).
- 배지 채우기는 T04·T07 이 끝나면 훨씬 싸진다 — 이 티켓은 **그때까지의 구조적 방어**다.

## Acceptance criteria

- AC1 — `/api/projects` 가 프로젝트 개수와 무관하게 빠르게 답한다(측정: 프로젝트 3개 기준 100ms 이하).
- AC2 — 선택된 프로젝트의 배지는 첫 화면에서 지금과 같은 값이다.
- AC3 — 안 센 프로젝트의 배지는 **비어 있고 0 이 아니다**.
- AC4 — 잠시 뒤 나머지 배지도 지금과 같은 값으로 채워진다.

## Verification

`pnpm verify` + `/api/projects` 응답 시간 측정. AC2~AC4 는 실제 화면에서 확인한다.

### 2026-09-04 (후속) — 🔴 **내가 이 티켓에서 넣은 결함을 캡틴이 잡으셨다**

> **"좌측 프로젝트 목록에 gootte 쪽에 1이 보이는데, 남아있는 피처 카드가 하나도 없는데 왜 1일까?"**

**재현됐다.** 같은 서버에서 두 라우트가 어긋났다:

```
GET /api/projects        → gootte openFeatures = 1
GET /api/features/gootte → 남은 일 있는 기능 0개
```

그리고 `/api/features/gootte` 를 한 번 부르고 나면 배지가 0 으로 고쳐졌다 — **그 프로젝트를
직접 열어야만 고쳐진다**는 뜻이다.

**원인 — 캐시를 만들고 무효화를 안 만들었다**

이 티켓이 배지를 `openCountBySlug` 에 기억시키면서, `scheduleCountFill` 을 **값이 없는 칸만
채우도록** 짰다. 그래서 한 번 세어진 배지는 문서가 아무리 바뀌어도 그대로 굳었다.
거기에 첫 계산이 **부팅 직후의 낡은 스냅샷**에서 나오면(stale-while-revalidate, adr/0001)
그 낡은 값이 영구히 남았다. **INV-3(stale 뷰 금지) 위반이고, 내가 만든 것이다.**

**고친 것 — 무효화를 두 번, 순서를 지켜서**

| 언제 | 누가 | 왜 |
|---|---|---|
| 변경 신호가 온 즉시 | `server.ts` `onChange` | 낡은 값을 일단 버린다 |
| **스냅샷 갱신이 끝난 뒤** | `scheduleProjectUpdate` 의 broadcast 래퍼 | 🔴 **이게 핵심.** 첫 번째만 있으면 다시 센 값이 여전히 **낡은 스냅샷**에서 나와 그대로 굳는다 |

재검증기(`snapshotRevalidator.onChange`)에도 같은 무효화를 걸었다 — 부팅 직후 경로다.

**확인 (실제 앱)**

```
부팅 직후, 프로젝트를 한 번도 안 열고:  gootte=0  jinwooauto=11  voice-to-iterm=2
임시 기능 생성 → 배지: None → 1 → 1     (열지 않았는데 올라간다)
임시 기능 삭제 → 배지: None → 0 → 0     (다시 내려간다)
```

중간의 `None` 은 "아직 안 셌다" 이고 화면은 배지를 감춘다 — 🔴 **0 으로 거짓말하지 않는다.**

**회귀 추가** — `🔴 문서가 바뀌면 배지도 다시 센다 — 한 번 세어진 값이 굳지 않는다`.
프로덕션과 **같은 순서**(신호 → 스냅샷 갱신 → 두 번째 무효화)를 밟는다. 고치기 전에는 이 테스트가
바뀌기 전 값을 그대로 냈다.
