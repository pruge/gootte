# T07 — 계산을 워커 스레드로 빼고, 문서 클릭이 아무것에도 줄 서지 않게 한다

**Blocked by:** T05, T06

**Time:** started=2026-09-04T12:00:40+09:00 finished=2026-09-04T12:10:19+09:00

## Goal

B·C·D 계산을 요청 스레드 밖(워커 스레드)으로 옮겨, **드로어 클릭이 어떤 계산에도 줄 서지 않는다**
는 성질을 구조로 보장한다.

## Why this slice

캡틴의 원래 요구다 — *"문서라는 게 바로 클릭하면 읽혀야 된다"*. 앞 티켓들이 계산을 작게(T02·T04)
드물게(T05·T06) 만들었지만, **동기인 한 최악의 경우는 남는다.** 워커로 옮겨야 "마지막 값 즉시 +
준비되면 교체" 라는 이 저장소의 원래 의도(adr/0001, `fast-cold-start`)가 실제로 성립한다.

## Produces

- 워커에서 도는 파생물 계산과, 요청 스레드가 **기다리지 않고** 마지막 값을 내주는 창구
- A 등급(원문) 경로의 격리 — B·C·D 를 한 글자도 건드리지 않는다
- 그 격리를 지키는 회귀 가드

## Consumers

없음(마지막 티켓).

## Touched surfaces

`backend/src/` 전반(워커 경계 신설) · `backend/src/app.ts`(`featuresFor`·`inProgressFor`·문서 라우트) ·
`core-io/`(순수하게 유지 — 워커에서 그대로 부를 수 있어야 한다)

## Explicitly out of scope

- 계산 로직 변경 — **옮기기만 한다.** 같은 입력에 같은 출력이어야 한다(INV-4).
- 화면 변경 — 값이 늦게 오는 자리는 이미 T03 이 다뤘다.
- 관리대상 쓰기(INV-2) — 워커도 읽기 전용이다.

## Locked decisions

- **D1** — 워커 스레드로 분리한다(캡틴, 2026-09-04).

## Evidence anchors

- `spec.md` §4 원인 A — 전부 동기라 이벤트 루프가 멈춘다. 드로어 요청은 소켓 큐에서 파싱조차 안 된다.
- `spec.md` §3 — `readFeatureDoc` 은 1ms 다. 느린 것은 그 앞의 줄이다.
- `backend/src/app.ts` 문서 라우트 — 지금 `withWorktrees(proj.copies)` 를 지나 같은 스레드에 선다.

## Regression guards

- 🔴 **같은 입력에 같은 출력** — 워커로 옮긴 뒤 기존 테스트 전부가 통과해야 한다. 하나라도 기대값을
  고쳐야 한다면 멈추고 왜인지 보고한다.
- 🔴 **워커가 죽어도 서버가 죽지 않는다** — 계산이 막히면 마지막 값을 계속 내주고, 막혔다는 사실을
  숨기지 않는다(INV-U1: 조용한 실패 금지).
- 🔴 **INV-3 를 잃지 않는다** — 워커가 늦는 동안 화면이 낡은 값을 보이는 것은 허용되지만, **준비되면
  반드시 교체**돼야 한다. 교체 신호가 안 가는 경로가 하나라도 있으면 영구 stale 이다.
- 🔴 **관리대상에 쓰지 않는다**(INV-2) — 워커도 마찬가지다.

## Scope

1. 워커 경계를 정한다 — 무엇을 보내고 무엇을 받는가(경로 목록 → 파생물, 직렬화 가능해야 한다).
2. `core-io` 의 계산부가 워커에서 그대로 도는지 확인한다(현재 순수 IO+계산이라 가능해야 한다).
3. 요청 스레드는 **절대 기다리지 않는다** — 캐시가 비면 빈 값/마지막 값을 즉시 내고 계산을 예약한다.
4. 계산이 끝나면 WS 로 교체를 알린다(지금 어휘 그대로).
5. 🔴 문서 라우트에서 B·C·D 를 건드리는 코드를 전부 떼어 낸다.
6. A 등급 격리 회귀 가드를 넣는다 — 무거운 계산이 도는 **동안** 문서 요청이 즉시 답하는지 보는 테스트.

## Implementation notes

- 6번 가드가 이 티켓의 값어치다. 그것 없이는 다음 사람이 문서 라우트에 계산을 다시 얹는다 —
  **지금 이 구조가 정확히 그렇게 생겼다.**
- 워커가 하나면 계산이 직렬화된다. 그것으로 충분한지, 풀이 필요한지는 측정 후 정한다 —
  **추측으로 풀을 만들지 마라.**
- `GOOTTE_DATA_DIR` 접근이 워커와 메인에서 겹치면 잠금 문제가 생긴다. 쓰기 주체를 하나로 유지해라.

## Acceptance criteria

- AC1 — jinwooauto 를 풀 재계산시키는 **동안** 문서 클릭이 **100ms 이내**에 답한다.
- AC2 — 앱을 처음 켠 직후 문서 클릭이 계산을 기다리지 않는다.
- AC3 — 기존 테스트 전부 통과, 기대값 수정 없음.
- AC4 — 워커를 일부러 죽여도 서버가 살아 있고, 막혔다는 사실이 드러난다.
- AC5 — 계산이 끝나면 화면이 새 값으로 교체된다.
- AC6 — AC1 을 지키는 회귀 테스트가 있다.

## Verification

`pnpm verify` + AC1·AC2 실측(실제 dev 서버, 격리 사본에서 자기 포트로).
