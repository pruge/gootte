# T04 — 문서 파생물(B)의 재계산 단위를 기능 폴더로 내린다

**Blocked by:** T02

**Time:** started=2026-09-04T11:46:59+09:00 finished=2026-09-04T11:53:08+09:00

## Goal

`readFeatures` 가 "프로젝트 전체를 다시" 계산하는 것을 멈추고, **기능 폴더 하나**를 단위로
계산·캐시·무효화한다.

## Why this slice

이 기능의 심장이다. 지금은 문서 한 장이 바뀌어도 기능 61개 × 사본 4개가 다시 돈다(spec §4 원인 B).
단위가 폴더로 내려가면 대부분의 재계산이 수십 ms 가 되고, 그 뒤에야 감시(T05)·git 축소(T06)·
워커 분리(T07)가 각각 제 값을 한다. **단위를 안 내리고 워커로 옮기면 5초짜리 계산이 옆 스레드에서
5초 도는 것뿐이다.**

## Produces

- 기능 폴더 단위 파생물 캐시(`<프로젝트> / <기능 slug>` → 파싱 결과)와 그 무효화 창구
- 폴더 단위 결과를 모아 지금과 **같은 모양**의 `Feature[]` 를 내는 조립 자리

## Consumers

T05(감시) — 이벤트가 무효화할 대상이 이 창구다. T07(워커) — 워커로 옮길 계산 단위가 이것이다.

## Regression guards

- 🔴 **여러 사본 합집합 규칙이 그대로다** — 같은 기능 폴더가 사본 여럿에 있으면 합집합이고,
  `Time:` 은 정방향 병합이며(T05 테스트 묶음), 갈라짐 판정도 같다. **폴더 단위 캐시는 그 폴더의
  모든 사본 판을 함께 갖는다** — 사본 하나만 캐시하면 합집합이 깨진다.
- 🔴 **정렬은 여전히 `applyInProgress` 뒤에 정해진다**(`features.ts:448` 주석) — 폴더 단위로
  계산한다고 목록 순서를 여기서 정하지 않는다.
- 🔴 **stale 을 새로 만들지 않는다**(INV-3) — 무효화 창구를 안 부르는 경로가 하나라도 남으면
  그 폴더는 영원히 낡는다. 무효화 지점을 전부 세어 문서에 적는다.
- 🔴 기존 `core-io/src/features.test.ts` 전부 통과.

## Scope

1. 한 기능 폴더 + 그 폴더를 가진 사본들 → 파생물 하나를 내는 함수를 가른다.
2. 그 결과를 폴더 단위로 캐시하고, 키에 **사본 구성**을 포함한다(사본이 늘거나 줄면 다른 값이다).
3. 무효화 창구를 만든다: `invalidate(project, featureSlug)` · `invalidateProject(project)`.
4. `featuresFor`·`updateProjectSnapshot` 이 이 창구를 쓰게 바꾼다.
5. 무효화되지 않은 폴더는 다시 읽지 않는다.

## Implementation notes

- 캐시 키에 무엇이 들어가야 하는지부터 적어라 — 사본 목록 · 각 사본의 그 폴더 mtime(또는 파일 목록+mtime).
  🔴 **mtime 하나로 폴더 전체를 대표하지 마라** — 하위 파일 변경이 폴더 mtime 을 안 올리는 경우가 있다.
- `codegraph impact "readFeatures"` 를 **편집 전에** 돌린다 — 호출부가 backend·cli 양쪽에 있다.
- 지금의 디스크 스냅샷(`plan.db`)과 어떻게 공존할지 정해라 — 폴더 단위 캐시가 스냅샷을 **대체**하는
  것이 자연스럽다. 대체한다면 `fast-cold-start` 의 "재기동에도 즉시" 성질을 유지해야 한다(adr/0001).

## Acceptance criteria

- AC1 — 기능 폴더 하나의 `.md` 를 고치면 **그 폴더만** 다시 계산된다(계산 횟수로 확인).
- AC2 — 나머지 폴더의 파생물은 재계산 없이 그대로 쓰인다.
- AC3 — 화면에 나가는 `Feature[]` 가 변경 전과 **같다**(같은 픽스처에 같은 결과).
- AC4 — 사본이 늘거나 줄면 그 폴더의 캐시가 무효가 된다.
- AC5 — jinwooauto 기준 "한 폴더만 바뀌었을 때" 재계산 시간이 수십 ms 대다.

## Comments

### 2026-09-04 — 완료. 안 바뀐 프로젝트 재계산 2,669ms → **358ms**.

**한 일**

`readFeatures` 를 세 단계로 갈랐다:

1. **사본별 HEAD** 를 먼저 얻는다(사본당 1회, T06 의 `CopyResolver` 기억 재사용).
2. **폴더 지문** — 내용을 **읽지 않고** (경로 · mtimeMs · 크기)만 stat 으로 모은다(`folderFingerprint`).
3. **캐시 조회** — 키가 같으면 그 폴더는 한 글자도 다시 읽지 않는다. 다른 폴더만 `walkSlug` →
   `buildDocTree` → `checkIgnored` → `mergeSlug` 를 탄다. 🔴 그 사본에서 다시 읽을 폴더가 하나도
   없으면 **`check-ignore` 도 안 부른다**.

**🔴 stale 을 새로 만들지 않는 방법 — 무효화 창구가 아니라 파생 키**

티켓은 `invalidate(project, feature)` 창구를 만들라고 했지만, **창구를 안 부르는 경로가 하나라도
남으면 그 폴더는 영원히 낡는다**(가드가 지적한 위험). 그래서 창구 대신 **키를 현재 상태에서
파생**시켰다 — 무효화를 "깜빡할" 수 있는 자리가 아예 없다. 키에 들어가는 것:

| 축 | 왜 |
|---|---|
| 유효 사본 목록 + **각 사본의 HEAD** | `resolveFile` 이 조상 관계로 나중 판을 고른다 → **커밋이 결과를 바꾼다**(T06 조사) |
| 폴더 안 모든 파일의 (경로 · mtimeMs · 크기) | 내용을 안 읽고 얻는 지문 |

Map 의 열쇠는 `사본목록 + slug`, HEAD·지문은 **값 쪽**에 둔다 — 커밋할 때마다 새 칸이 생겨
Map 이 무한히 자라는 것을 막고, 다른 프로젝트가 같은 slug 를 가져도 서로의 칸을 안 밀어낸다.
`clearFeatureCache()` 도 함께 냈다(테스트·명시적 무효화용).

**결과 순서**를 폴더 훑은 순서 그대로 유지했다 — 캐시 적중 여부가 목록 순서를 바꾸면 화면이
이유 없이 흔들린다.
