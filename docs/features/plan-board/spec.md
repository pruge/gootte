# 계획은 판 위에서 움직인다

**Status:** draft (2026-08-12)

기능 카드를 **다섯 자리** 사이로 옮기는 판 하나가 계획의 전부다.
자리는 캡틴이 정하고, 나머지는 전부 문서에서 저절로 나온다.

🔴 이 기능은 [`development-order`](../development-order/spec.md) 를 **대체한다.**
그 기능은 폐기했고 되살리지 않는다 — 개념이 다르지 개선이 아니다.

## 문제 — 셋 다 한 뿌리에서 나왔다

캡틴이 세 가지를 지적하셨다. 코드를 읽어 보니 **원인이 하나**다.

| 캡틴이 본 것 | 실제 원인 |
|---|---|
| ① 문서를 써도 planner 가 gootte 에 등록하지 않는다 | 등록이 **손으로만** 되는 구조다. 문서에서 계획으로 가는 자동 경로가 **한 줄도 없다** |
| ② 어긋남의 정의가 이상하다 | 어긋남은 ①의 증상을 사후에 세는 장치였다. 원인을 없애면 셀 것이 없다 |
| ③ 문서와 실시간 연동이 안 된다 | 실시간 배선은 이미 있다. 연동이 안 보인 것은 **계획 쪽 절반이 손으로 넣은 사본**이었기 때문이다 |

🔴 **어긋남은 문제가 아니라 흉터였다.** 계획을 사람이 손으로 심고 문서를 따로 움직이니
둘이 갈라지는 것이 필연이었고, 갈라진 것을 세는 목록이 어긋남이었다.
심는 행위를 없애면 갈라질 두 축이 없다.

## 모델 — 자리 하나, 단계 하나

### 다섯 자리

| 자리 | 어떻게 들어가나 | 누가 결정하나 |
|---|---|---|
| **대기** | 자리 행이 없는 모든 기능 문서 | 아무도. 문서를 쓰면 저절로 |
| **작업 대상** | 캡틴이 끌어다 놓음 | 캡틴 |
| **예약** | 캡틴이 내림 | 캡틴 |
| **폐기** | 캡틴이 옮김 | 캡틴 |
| **완료** | 티켓이 전부 `[x]` 되거나, 캡틴이 남은 것을 안은 채 옮김 | 문서 또는 캡틴 |

🔴 **대기는 저장하지 않는다.** 자리 행이 없다는 것이 곧 대기다.
그래서 "등록"이라는 행위가 사라진다 — 없는 행위는 빠뜨릴 수 없다(문제 ①).

### 저장 형태 — 표 둘

```
placement (project, feature)             ← 열쇠
  area        작업대상 | 예약 | 폐기 | 완료
  seq         작업 대상 안에서의 카드 순서
  closed_at   완료 칸에 들어간 시각 (날짜+시간)

step (project, feature, ticket)          ← 열쇠
  step        1 이상의 정수
```

버리는 것: `트랙`, `순위(실수 rank)`, `왜`, `왜 닻` 셋, `opinion_request`, `extra`, `history.md`.

### 쓰는 사람이 셋뿐이다

| 누가 | 무엇을 |
|---|---|
| 캡틴 | `area`, `seq` — 드래그 또는 카드 머리의 대화상자 |
| firstmate | `step` — 티켓마다 하나 |
| gootte 자신 | 닫히는 순간 하나(아래) |

🔴 **planner 는 계획 DB 에 아무것도 쓰지 않는다.** 문서만 쓴다.
이것이 캡틴의 관점 2("ai 관여를 최소로")에 대한 답이다.

### gootte 가 스스로 쓰는 단 한 순간

한 기능의 티켓이 전부 `[x]` 인 것을 처음 보면 `area=완료` 와 `closed_at` 을 적는다. 그것뿐이다.

🔴 **완료에서 나오는 길은 캡틴뿐이다.** 자동으로 되돌아 나오는 경로를 만들지 않는다.

### 🔴 닫힌 기능에는 티켓을 더하지 않는다 (캡틴 결정)

더 할 일이 생기면 **새 기능을 세워 시작한다.** 닫힌 기능에 티켓을 덧붙이지 않는다.

이것은 규율이지 코드가 막는 것이 아니다. 그래서 gootte 는 이 경우를 위한 장치를
**하나도 짓지 않는다** — 닫을 때 티켓 목록을 기억해 둘 필요도, 새 번호가 나타났는지 감시할 필요도,
자동으로 대기로 되돌릴 필요도 없다. 규율을 어겨 티켓이 하나 붙으면 카드는 완료 칸에 머문 채
빈 상자를 하나 보여 준다 — 덮어 닫은 카드와 같은 모습이고, 캡틴이 보고 정하시면 된다.

🔴 **이 결정이 설계를 줄였다.** 규율 한 줄이 저장 칸 하나와 자동 규칙 하나를 통째로 없앴다.

### 완료가 둘로 갈리는 자리

| | 어떻게 | 카드가 보이는 모습 |
|---|---|---|
| 저절로 닫힘 | 티켓 전부 `[x]` | 상자 전부 채워짐 |
| 덮어 닫음 | 캡틴이 남은 것을 안고 옮김 | 안 채운 상자가 그대로 보인다 |

🔴 **남은 티켓을 지우거나 완료로 위장하지 않는다.** 상자는 빈 채로 카드에 남는다.
왜 남기고 닫았는지는 **그 티켓 문서에 적는다**(캡틴 결정). gootte 는 이유를 받지도 저장하지도 않는다 —
카드 머리의 첫 아이콘이 그 문서로 가는 길이다.

### 완료 카드는 접혀 있다 (캡틴 결정)

완료 칸의 카드는 **머리만 보이게 접혀** 있다. 눌러야 티켓 목록이 펼쳐진다.
끝난 일이 화면을 차지하지 않게 하되 사라지지도 않게 한다 — 덮어 닫은 카드의 빈 상자도
펼치면 그대로 보인다(INV-B4). 접힘은 **화면의 상태**이지 저장하지 않는다.

### 단계

- firstmate 가 티켓마다 정수를 준다. 연속이며 상한은 없다(캡틴 결정: "단계는 연속").
- 🔴 **저장한 숫자는 아무도 고치지 않는다.** 화면에 그릴 때 **빈 단계를 걷어내며 1부터 다시 센다.**
  그래서 "1단계가 비면 1,2,3,4 가 된다"가 아무도 손대지 않아도 성립한다.

### 🔴 단계는 잠시 붙었다 사라지는 것이다 (캡틴 결정)

> "단계는 애초에 문서에 있으면 안되. db에 잠시붙었다가 사라지는거잖아."

두 가지가 따라 나온다.

**하나 — 단계를 문서에 적지 않는다.** 단계도, 왜 그 단계인지도. 티켓 문서가 갖는 것은
무엇을 기다리는가(`Blocked by:`)와 무엇을 만드는가이며, 그것은 그 티켓의 성질이라 낡지 않는다.
단계는 지금 이 판의 사정이라 내일이면 다른 값이다. 낡을 것을 안 낡는 곳에 적지 않는다.

**둘 — 단계는 작업 대상에 있는 동안만 존재한다.** 기능이 작업 대상을 떠나면(예약·폐기·완료
어느 쪽이든) 그 기능 티켓들의 단계 행을 **지운다.** 다시 올리면 firstmate 가 다시 매긴다.

남겨 두면 아무도 실행하지 않는 계획의 숫자가 DB 에 눌러앉는다 — 되올릴 때 그것이 아직 맞는지
아무도 확인하지 않으므로, 그 순간 낡은 계획이 새 계획인 척한다.
다시 매기는 값은 한 번의 명령이고, 낡은 숫자를 되살리는 값은 잘못된 순서다.

### `next`

작업 대상에 있는 기능의, 표시 기준 **1단계 티켓만** 내보낸다.
트랙 묶음 없다. 어긋남 없다(INV-B3). 정렬은 `seq`(카드 순서) 다음 티켓 번호.

## 명령 — `pnpm gootte`

자리를 캡틴이 브라우저에서 정하므로 CLI 에서 할 일이 거의 없어진다.

| 명령 | 무엇 | 누가 |
|---|---|---|
| `discover <…>` | 관리대상 발견 — **그대로** | 에이전트 |
| `db migrate` | 표 만들기·칸 채우기 — **그대로** | 에이전트 |
| `next <프로젝트>` | 작업 대상의 표시 1단계 티켓 — **의미가 바뀐다** | firstmate |
| `step <프로젝트> <기능>/<티켓> <N>` | 단계를 매긴다 — 옛 `set` 을 대체 | firstmate |
| `step --clear <프로젝트> <기능>/<티켓>` | 단계를 뗀다 — 옛 `drop` 의 티켓 절반 | firstmate |
| `board <프로젝트>` | 다섯 칸 현황을 읽는다 — 옛 `order` 를 대체 | 누구나 |

사라지는 것: `set` · `set-feature` · `drop` · `order` · `extra`.

🔴 **`--why` 를 받지 않는다.** 계획 DB 는 이유를 담지 않는다(§저장 형태).
🔴 **단계의 이유는 어디에도 남기지 않는다**(캡틴 결정: "남기지마"). 문서에도, DB 에도.
지금까지 적어 온 이유들을 다시 읽어 보면 대부분 막힘을 다시 말하거나 그때의 상태를 말한 것이었다 —
앞의 것은 중복이고 뒤의 것은 시간이 지나면 거짓말이 된다. 남길 자리를 만들면 그 자리가 낡는다.

### 🔴 자리를 옮기는 명령은 두지 않는다

`board` 는 **읽기 전용**이고, `area` 와 `seq` 를 바꾸는 CLI 는 만들지 않는다.
열어 두면 firstmate 나 planner 가 슬쩍 자리를 옮기게 되고, 그것은 캡틴이 지적하신 문제 ①이
반대 방향으로 되살아나는 것이다 — 이번에는 사람이 안 넣어서가 아니라 기계가 몰래 넣어서 갈라진다.
**자리는 캡틴의 손, CLI 는 읽기만.**

완료 칸 들고남은 예외가 아니다 — gootte 자신이 판정해서 쓰는 것이지 누가 명령해서 되는 것이 아니다.

🔴 `AGENTS.md` 의 명령 표는 이 문서가 고치지 않는다 — 01 과 05 가 배달 경로로 고친다.

## 신선함은 어디서 오나 (캡틴 관점 1)

| 화면이 말하는 것 | 어디서 오나 |
