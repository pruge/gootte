# 실측 — 큰 문서 클릭 → 본문 표시 (2026-09-04)

T01 의 산출물. **고치지 않았다 — 쟀다.**

## 방법

- 격리 환경: backend `:8899` + frontend `:5399`, `GOOTTE_DATA_DIR=~/.gootte-perf-t01`
  (캡틴의 `:8804`/`:5304` 와 `~/.gootte` 는 건드리지 않았다).
- 브라우저: `chrome-devtools-axi` 세션 `t01` (Chrome 152).
- 🔴 **`perf-start`/`perf-stop` 은 이 작업에 쓸 수 없었다** — 페이지 이동이 없는 상호작용이라
  trace 요약이 비어 나왔다. 대신 **Long Animation Frame(LoAF) API + Resource Timing** 으로 쟀다.
  LoAF 는 프레임을 `scripts` / `renderStart` / `styleAndLayoutStart` 로 갈라 주므로
  스크립팅과 스타일·레이아웃이 그 안에서 갈린다.
- 측정 구간: `pointerdown` → 본문 DOM 등장 → `requestAnimationFrame` 2회 뒤(= 페인트 완료).
- 각 표본 4회, 1회차는 fetch 를 타고 2회차부터는 react-query 캐시로 fetch 가 없다.

## 결과 — 프로덕션 빌드 (`vite build` + `vite preview`)

| 문서 | 크기 | 1회차(fetch 포함) | 2~4회차 | 그중 스크립팅 |
|---|---|---|---|---|
| `plan-board/spec.md` | 24,819자(렌더 후 21,044자) | **124.2ms** (fetch 22.0) | **87.1 · 81.8 · 84.5ms** | 68.0~71.7ms |
| `a-vanished-card-breaks-nothing/spec.md` | 1,341자(렌더 후 1,300자) | **50.9ms** (fetch 21.1) | **14.7 · 13.0 · 13.6ms** | 0 (긴 프레임 없음) |

dev 빌드(`vite dev`)도 같은 방법으로 쟀고 **프로덕션과 큰 차이가 없었다** — 큰 문서 156.7ms(첫 열기)
· 158.3ms(두 번째), 작은 문서 10~16ms.

## 🔴 전제가 재현되지 않았다

이 기능의 spec 은 T08 이 적은 **311~331ms** 를 전제로 세워졌다. **오늘 그 값이 나오지 않는다.**
가장 나쁜 값이 156.7ms 이고 warm 은 82~98ms 다.

오늘 한 번 **347.9ms** 를 봤는데, 그 표본은 `perf-stop` 직후 — **trace 오버헤드가 얹힌 것**이었다.
T08 의 숫자도 같은 조건에서 나왔을 가능성이 높다(T08 도 `perf-*` 를 켠 채 클릭했다).
🔴 **재지 않고 그 숫자를 이어 쓰지 않는다.** 이 저장소는 같은 실수를 두 번 했다
(`read-path-redesign/spec.md` §3.1 — PATH shim 7배, `npx` 8배).

덧붙여 T08 이 "18,320자" 라고 적은 것은 **바이트였다.** 같은 파일이 지금 12,512자 / 21,142바이트다.

## 84ms 의 내역 — 지배 구간이 없다

warm 82~87ms 를 세 조각으로 갈랐다. 어느 하나가 압도하지 않는다.

| 구간 | 실측 | 어떻게 쟀나 |
|---|---|---|
| 마크다운 파이프라인 (parse → gfm → hast) | **23~39ms** | Node 에서 저장소 자신의 `unified`·`remark-parse`·`remark-gfm`·`remark-rehype` 로 40회, 워밍업 10회 제외 후 min/median |
| DOM 생성 + 레이아웃 바닥값 | **15~28ms** | 렌더 결과 HTML(73,300바이트 · 1,072노드)을 detached div 에 `innerHTML` 로 넣고 강제 레이아웃, 5회 |
| 나머지 = React element 생성·재조정·커밋 | **~20~40ms** | 전체 − 위 둘 |
| fetch(서버) | **1.2~1.5ms**(API 단독) / 11~22ms(브라우저 왕복) | `curl` 5회 · Resource Timing |

즉 **서버는 이미 끝났고**(1.4ms), 남은 시간은 **클라이언트에서 셋으로 고르게 나뉜다.**
🔴 그래서 "여기 하나만 고치면 된다" 고 말할 수 없다. 하나를 지워도 3분의 1만 준다.

## 크기에 비례하는가

1,300자 → 13~15ms, 21,044자 → 82~87ms. 16배 커질 때 6배 느려졌다 —
**선형에 가깝되 고정비가 있다.** 문서가 두 배가 되면 대략 두 배를 각오해야 한다는 뜻이다.

## 곁다리 발견 — 번들이 한 덩어리다

`vite build` 가 경고한다: `dist/assets/index-*.js` **578.87kB(gzip 173.06kB) 단일 청크.**
`react-markdown`+`remark-gfm` 이 첫 화면 번들에 통째로 실린다. 이것은 문서 렌더 시간이 아니라
**첫 진입 비용**이므로 이 기능의 범위가 아니다 — 별개로 다룰 일이다.

## 🔴 재지 못한 것 — Tauri(WKWebView)

이 숫자는 전부 **Chrome** 에서 나왔다. **캡틴이 실제로 쓰는 것은 Tauri 데스크톱 앱이고 그 안은
WKWebView(Safari 엔진)다.** 엔진이 다르면 마크다운 파싱·재조정 비용이 같다는 보장이 없다.
캡틴 앱(`:8804`/`:5304`)이 떠 있었고 dev-server 규율이 그것을 건드리지 말라고 해서 재지 않았다.
**이 공백이 T02 다.**
