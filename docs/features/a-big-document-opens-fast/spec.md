# 큰 문서도 빠르게 열린다

## 문제

read-path 재설계(`read-path-redesign`)로 **서버 쪽 읽기 경로는 끝났다.** 문서 API 는 3~5ms 다.
그런데 캡틴이 문서를 클릭하고 본문을 보기까지는 여전히 눈에 띄게 걸린다 — **남은 시간이 전부
브라우저 안에서 쓰인다.**

T08 검수에서 실측한 것(2026-09-04, `read-path-redesign/tickets/T08.md`):

| 무엇 | 실측 |
|---|---|
| 문서 API(`GET /api/features/:slug/doc`) | **3~5ms** |
| 작은 문서 클릭 → 본문 표시 | **42ms** |
| 큰 문서(18,320자) 클릭 → 본문 표시 | **311~331ms** |

같은 API 를 통과했는데 차이가 7배 이상이다. 즉 **문서 크기에 비례하는 비용이 클라이언트에
있다.** 서버를 더 깎아도 이 300ms 는 줄지 않는다.

## 지금 구조 (실측)

`code/web/frontend/src/components/features/DocDrawer.tsx` 가 본문을 그린다.

```tsx
<ReactMarkdown remarkPlugins={[remarkGfm]} components={MD_COMPONENTS}>
  {data.content}
</ReactMarkdown>
```

- 렌더러 = `react-markdown@9` + `remark-gfm@4` (`code/web/frontend/package.json`)
- 문서 전체를 **한 번의 동기 렌더**로 파싱 + 리액트 트리 생성 + 커밋한다.
- 서랍이 열리는 커밋과 본문이 그려지는 커밋이 같다 — 그래서 파싱이 끝날 때까지 화면이 안 움직인다.

**단, 이 300ms 의 내역은 아직 측정되지 않았다.** 파싱(remark/mdast)인지, 리액트 트리 생성인지,
스타일·레이아웃인지, 폰트인지 갈리지 않았다. 🔴 **원인을 정하기 전에 고치지 않는다** — 이 저장소는
이미 한 번 짐작으로 최적화했다가 측정이 틀렸던 적이 있다(`read-path-redesign/spec.md` §3.1).

## 목적

**큰 문서를 클릭했을 때도 즉시 무언가가 보이고, 본문이 곧 따라온다.**
"전부 준비될 때까지 아무것도 안 보인다" 를 끝내는 것이 목적이지, 렌더 시간 자체를 0 으로 만드는
것이 목적이 아니다.

## 불변식 점검

- **INV-3(stale 뷰 금지)** — 무엇을 늦게 그리든 **결국 그려지는 것은 현재 SoT** 여야 한다.
  본문 일부만 그리고 마는 최적화는 금지.
- **INV-4(read-path 는 결정적)** — 마크다운을 요약하거나 잘라 보여주지 않는다. **verbatim 릴레이.**
- INV-1·INV-2·INV-5 는 해당 없다(이 작업은 아무것도 저장하지 않고 관리대상을 건드리지 않는다).

## 범위 밖

- 서버 읽기 경로 — 이미 3~5ms 다.
- 문서 목록·뱃지·감시 체계 — `read-path-redesign` 이 갖는다.
- 마크다운 렌더러를 바꾸는 결정 자체 — **측정 결과가 그것을 가리키면 그때 ADR 로 끊는다.**
