# T01 — 큰 문서 렌더 300ms 의 내역을 측정한다

**Blocked by:** 없음 — 즉시 착수 가능

**Time:** started=2026-09-04T16:07:17+09:00 finished=2026-09-04T16:19:33+09:00

## Goal

큰 문서 클릭 → 본문 표시까지의 **311~331ms 가 어디서 쓰이는지를 프로파일로 갈라낸다.**
고치는 것은 이 티켓의 일이 아니다 — **무엇을 고쳐야 하는지를 근거와 함께 확정하는 것**이 산출물이다.

## Why this slice

측정 없이 손대면 틀린다. 이 저장소는 read-path 재설계에서 **두 번 연속으로 측정이 틀렸고**
(PATH shim 이 git 호출을 7배, `npx` 가 8배 부풀렸다 — `read-path-redesign/spec.md` §3.1),
그 경험이 "짐작으로 고치지 않는다" 를 규율로 만들었다. 렌더 최적화는 특히 짐작하기 쉬운 자리다
(가상 스크롤? 증분 파싱? 렌더러 교체? — 셋 다 그럴듯하고 셋 다 근거 없이는 도박이다).

## Produces

`docs/features/a-big-document-opens-fast/` 아래:
- 프로파일 실측을 적은 문서 — **구간별 ms 와 그 근거(추적 파일·insight 이름)**
- 그 결과가 가리키는 처방을 **후속 티켓(T02…)으로 끊은 것**

## Consumers

캡틴(무엇을 고칠지 판단) · 후속 티켓의 작업자.

## Touched surfaces

**측정만이므로 제품 코드는 건드리지 않는 것이 기본이다.** 계측을 위해 임시 코드를 넣었다면
이 티켓이 끝날 때 **되돌린다**(남기려면 그 자체를 후속 티켓으로 끊는다).

- 읽는 곳: `code/web/frontend/src/components/features/DocDrawer.tsx` ·
  `code/web/frontend/src/lib/query.ts` · `code/web/frontend/package.json`

## Explicitly out of scope

- 고치는 것(렌더러 교체 · 증분 렌더 · 가상 스크롤 · 서버 사전 파싱) — 전부 후속 티켓.
- 서버 읽기 경로 — 3~5ms 로 이미 끝났다.

## Locked decisions

- **도구는 `chrome-devtools-axi`** — `perf-start` / `perf-stop` / `perf-insight`.
  ego-browser 로는 이 축을 잴 수 없다. 고르는 기준은 스킬 `gootte-browser` 가 SoT 다.
- **처방을 이 티켓에서 구현하지 않는다.** 측정 → 판단 → 티켓, 거기까지다.

## Evidence anchors

- `docs/features/read-path-redesign/tickets/T08.md` — 42ms(작은 문서) vs 311~331ms(18,320자 문서),
  같은 API 3~5ms.
- `read-path-redesign/spec.md` §3.1 — 측정이 틀렸던 두 사례와 정정된 숫자.
- 렌더 호출부: `DocDrawer.tsx` 의 `<ReactMarkdown remarkPlugins={[remarkGfm]} …>` 한 곳.

## Regression guards

- 이 티켓은 동작을 바꾸지 않는다 — `pnpm verify` 가 green 인 채로 유지되는 것이 가드다.
- 계측 코드를 넣었다면 **`git diff` 가 비어 있는 것**으로 되돌림을 확인한다.

## Scope

1. dev 서버를 띄운다 — 🔴 **띄우기 전에 스킬 `gootte-dev-server`**(`GOOTTE_DATA_DIR` 격리).
2. `chrome-devtools-axi perf-start` → 큰 문서 클릭 → `perf-stop` → `perf-insight`.
   - 큰 문서 = `read-path-redesign/spec.md`(실측 당시 18,320자, 이후 커져 지금 21,142바이트 —
     **다시 재고 그 값을 적는다**).
   - 대조군으로 작은 문서도 같은 방법으로 한 번.
3. 구간을 가른다: 네트워크 / 파싱(remark·mdast) / 리액트 렌더 · 커밋 / 스타일·레이아웃 · 페인트.
4. 지배 구간이 나오면 **그것을 줄이는 처방을 티켓으로 끊는다**(하나가 아니면 여러 장).
5. 🔴 **갈라지지 않으면 갈라지지 않았다고 적는다.** 그럴듯한 원인을 지어내지 않는다.

## Implementation notes

- `react-markdown@9` 는 매 렌더마다 문자열을 다시 파싱한다. 서랍을 여닫으면 그 비용이 반복되는지도
  같이 본다(같은 문서를 두 번째 열 때의 숫자를 따로 적는다).
- 폰트(Pretendard)나 코드블록 스타일이 지배할 가능성도 배제하지 않는다 — 측정이 정한다.
- 숫자는 **한 번 재고 끝내지 않는다.** 최소 3회, 값의 범위를 적는다(T08 이 311~331ms 로 적었듯이).

## Acceptance criteria

- AC1 — 큰 문서 1회 렌더의 **구간별 ms 가 문서에 적혀 있고**, 각 숫자에 추적 근거가 붙어 있다.
- AC2 — 작은 문서 대조군 숫자가 같은 방법으로 적혀 있다.
- AC3 — **지배 구간이 지목되어 있거나**, 지목할 수 없다는 사실과 그 이유가 적혀 있다.
- AC4 — AC3 이 지목한 것을 고치는 **후속 티켓이 실제로 존재한다**(지목 실패면 그 사실이 spec 에 반영).
- AC5 — 제품 코드에 계측 잔재가 없다(`git diff` 로 확인).
- AC6 — `pnpm verify` green.

## Verification

```
pnpm verify
git status --porcelain code/web        # 계측 잔재 없음
```
프로파일 자체는 `chrome-devtools-axi perf-insight` 출력으로 검증한다.
