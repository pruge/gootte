# T02 — 여러 사본의 기능 문서를 합치고, 나중 판을 고른다

## Goal

한 프로젝트의 사본이 여럿일 때 그 `docs/features/` 를 **합집합**으로 읽는다.
같은 파일이 여러 사본에 있으면 **나중 판**의 내용을 쓴다 — 판정은 저장소가 답하는 사실이지 추정이 아니다.

## Why this slice

캡틴이 원하신 것의 본체다. T01 이 만든 사본 목록 위에 서고, 이 티켓만으로는 화면이 안 변한다
(지금 뿌리는 사본을 하나씩만 준다) — 실제 활성화는 T05 다.

## Produces

`readFeatures(copies: string[])` 와 `readFeatureDoc(copies, feature, path)` — 사본 목록을 받아
합쳐진 결과를 내는 읽기 계층. 파일 하나당 **어느 사본이 이겼는지**의 판정.

## Implementation notes

- 기능 폴더(slug)와 그 안의 파일을 **상대 경로 키**로 합친다. 한쪽에만 있으면 그대로 들어온다.
- 양쪽에 있고 바이트가 다르면 `spec.md` 절차대로: 미커밋 있는 쪽 → HEAD 후손 쪽 → 못 고름.
  - 미커밋 여부는 `git status --porcelain -- <상대경로>` 로 그 **파일만** 묻는다(사본 전체를 훑지 않는다).
  - 후손 판정은 `git merge-base --is-ancestor <A> <B>` 두 방향. 실측 7ms — 파일마다 불러도 무방하지만,
    사본 쌍당 **한 번** 구해 재사용한다.
- 🔴 경로 탈출 차단은 **사본마다** 판정한다. base 가 사본 수만큼 있으므로, 한 사본에서 통과했다고
  다른 사본 경로를 열어 주면 안 된다.
- `git` 이 답하지 않는 사본(저장소가 아님·깨짐)은 **그 사본만 건너뛴다** — 나머지는 그대로 보인다.

## Acceptance criteria

1. 사본 A 에만 있는 기능이 결과에 뜬다.
2. 사본 B 에만 있는 기능도 뜬다.
3. 양쪽에 있고 내용이 같으면 한 벌만 뜬다.
4. 양쪽에 있고 B 만 미커밋 변경이 있으면 **B 의 내용**이 뜬다.
5. 양쪽 다 커밋 상태이고 B 의 HEAD 가 A 의 후손이면 **B 의 내용**이 뜬다.
6. 어느 방향으로도 조상이 아니면 **고르지 않고** 그 사실이 결과에 실린다(표시는 T03).
7. 사본 하나뿐이면 결과가 지금과 **바이트로 동일**하다.
8. 사본 경로 하나가 없거나 저장소가 아니어도 나머지가 그대로 뜬다.
9. 문서 원문 서빙이 각 사본의 경계 밖 경로를 거절한다.
10. `pnpm -C code/web verify` green.

## Verification

routine. 🔴 **픽스처는 실물에서 떠 온다** — 임시 디렉토리에 진짜 git 저장소 두 벌을 만들어
조상 관계와 미커밋 상태를 실제로 만든다. `git status`·`merge-base` 출력 모양을 지어내지 않는다
(지어낸 픽스처가 착지 후 한 번도 동작 안 한 기능을 통과시킨 전례가 이 저장소에 있다).
