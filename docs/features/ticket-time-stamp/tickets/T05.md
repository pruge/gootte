# T05 — 여러 사본의 `Time:` 줄을 정방향으로 합치고, 실시간 갱신 공백을 고친다
Time: started=2026-08-29T14:01:16+09:00 finished=2026-08-29T14:01:16+09:00

## Goal

`Time:` 줄이 main과 항해사(secondmate) 등 **여러 사본**에 흩어져 있을 때, 화면이 항상
"지금까지 관측된 가장 완전한 시각"을 보여주게 한다 — 어느 사본에 `Time:`이 없다고 해서
다른 사본이 이미 기록한 값이 화면에서 사라지면 안 된다(정방향 전용 병합).
동시에, CLI로 `Time:` 줄을 막 기록했는데 화면이 수동 새로고침 전까지 낡은 상태를 보이는
실시간 갱신 공백을 찾아 고친다.

## Why this slice

T04가 완료 판정을 git·백로그에서 `Time:` 줄 하나로 옮겼다. 그런데 실측(2026-08-29,
캡틴 직접 확인)으로 두 가지 문제가 드러났다:

1. **여러 사본 병합이 "정방향"이 아니다.** 지금 문서 병합(`mergeSlug`/`resolveFile`,
   `core-io/src/features.ts`)은 파일 전체를 통째로 "나중 판" 하나만 고른다(커밋 조상
   관계 또는 미커밋 여부로 승자 결정). `Time:` 줄이 있는 사본과 없는 사본이 우열을
   가릴 git 관계가 없으면(진짜 갈라짐, case c) **대표 사본(`copies[0]`, 보통 main)의
   내용을 쓴다** — main에 `Time:`이 없으면 다른 사본에 있어도 화면엔 안 뜬다.
2. **실시간 갱신이 한 번 안 됐다.** T01·T02·T04에 `gootte start`/`end`로 `Time:`을
   기록한 직후 화면은 T04를 "처리중"으로 계속 보였고, 수동 새로고침 후에야 "완료"로
   바뀌었다(캡틴 실측, 2026-08-29). 원인 미상 — 이 티켓이 재현하고 고친다.

## 캡틴 지시 원문 (설계 방향)

> "gootte는 main과 각 2nd 의 폴더를 감시하고 있잖아. 따라서 started와 finished를
> 문서를 읽을때 규칙을 정해야할꺼 같아.
> a. 1차 main을 스캔해서 cache에 기록.
> b. 2차 2nd 스캔해서 cache 업데이트. 정방향(그러니까 있다가 없지는것은 안되고,
>    없다가 있는 쪽으로만 갱신가능)"
>
> "내가 main에서 직접 수정한경우 2nd에는 start가 없고, main만 start가 있는경우도
> 해결할수 있지 않아."
>
> (부하 우려에 대해) "만약 프로젝트들의 개수가 계속 늘어난다면, 이거 점점 부하걸리는것
> 아니야? 매번 새롭게한다면?"
>
> (git 사용 범위 확인 후) "a로 진행하고" — **완료 판정용 git은 계속 제거된 채로 유지**
> (T04/ADR-0001 그대로), **변경 감지용 git(HEAD 스탬프 캐시 게이팅)은 유지** — 이건
> "캐시가 낡았는지" 판정용일 뿐 완료/시작 여부를 결정하지 않는다.

## Produces

1. **`Time:` 필드 전용 정방향 병합** — `startedAt`/`finishedAt`을 문서 전체의
   "나중 판" 로직과 분리해서, **사본별로 각각 읽고 값이 있는 쪽이 이긴다**:
   - 어떤 사본이든 `startedAt`이 있으면 그 값을 쓴다(없는 사본이 있는 사본의 값을
     지우지 못한다).
   - `finishedAt`도 같은 규칙 — 한 사본이라도 `finished`를 기록했으면 화면은 완료로
     본다.
   - 두 사본이 서로 다른 `Time:` 값을 **둘 다** 갖고 있으면(예: 각각 다른 시각에
     start를 두 번 찍음) — 이 경우의 처리 규칙은 구현 중 결정하되, 안전 쪽으로
     기운다(먼저 시작한 시각을 startedAt으로, 나중에 끝난 시각을 finishedAt으로 등
     — 캡틴 워크플로가 한 사본에서만 start/end를 부르는 것이 정상 경로이므로 흔치
     않은 경우다).
   - 이 병합은 사본 전체 파일의 "나중 판" 결정(`resolveFile`)과는 **별개**다 —
     `Time:` 값만 이 새 규칙을 따르고, 티켓 문서의 나머지 내용(제목·본문 등)은
     기존 방식 그대로 둔다.

2. **캐시 재사용으로 부하 억제** — 프로젝트/항해사 수가 늘어도 매 요청 전체 재계산이
   되지 않게, 이미 있는 git HEAD 스탬프 게이팅 패턴(`fast-cold-start`,
   `code/web/backend/src/snapshot.ts`의 `sameStamps`/`recordProjectScan` 방식)을
   재사용한다. 사본의 HEAD가 안 바뀌었으면 그 사본의 `Time:` 값도 캐시에서 그대로
   쓴다 — 매번 처음부터 다시 스캔하지 않는다.
   🔴 **주의**: 이 스탬프는 오직 "이 사본이 마지막 스캔 이후 바뀌었는가"만 판정한다.
   완료/시작 여부 판정에는 절대 관여하지 않는다(T04/ADR-0001 유지) — git을 다시
   완료 판정에 끌어들이면 안 된다.

3. **실시간 갱신 공백 조사·수정** — `gootte start`/`end`로 파일을 편집한 직후
   화면이 수동 새로고침 없이 반영되는지 확인하고, 안 되면 원인을 고친다. 확인할 곳:
   - `code/web/core-io/src/watch.ts`의 `chokidar.watch(contentPaths(...))` —
     항해사 홈의 `docs/features` 경로가 실제로 감시 대상에 포함되는지
     (`deriveWatchRoots` → `discoverProjects` → `contentPaths`).
   - `awaitWriteFinish`(안정화 80ms) + debounce(150ms) 타이밍이 CLI의 빠른
     `start`+`end` 연속 호출(수 초 이내)과 충돌하는지.
   - 프론트 `live.ts`의 쿼리 무효화(`predicate: q.queryKey.includes(ev.project)`)가
     `Time:` 값이 반영되는 쿼리 키를 실제로 잡는지.
   - React Query의 `staleTime`/캐시 설정이 invalidate 이후에도 재요청을 늦추는지.

## Explicitly out of scope

- 완료 판정 로직 자체 재설계 — `joinTicket`의 3단 규칙(`finishedAt`→done,
  `startedAt`만→in_progress, 없음→pending)은 T04 그대로 유지한다.
- git을 완료 판정에 다시 쓰는 것 — 명시적으로 금지(캡틴 확인, "a로 진행").
- 구관례(`issues/`) 티켓의 시간 기록 — 범위 밖.
- localStorage(브라우저 저장소) 도입 — 캡틴이 이 아이디어를 제안하셨으나, 서버 쪽
  캐시(스냅샷 파일)로 이미 같은 문제를 풀고 있어 프론트 저장소는 필요 없다고
  판단됨(이 판단이 틀렸다면 needs-decision으로 올릴 것).

## Locked decisions

- 🔴 **정방향 전용**: `Time:` 필드는 "있다가 없어지는" 방향의 갱신을 허용하지 않는다
  — 어느 사본이든 값을 기록하면 그 값은 다른 사본에 없다는 이유로 사라지지 않는다.
- 🔴 **git은 변경 감지 전용으로만 유지** — 완료/시작 판정에는 여전히 `Time:` 줄만
  쓴다(T04/ADR-0001 무손상).
- 🔴 **성능**: 프로젝트·항해사 수 증가에 매 요청 전체 재스캔으로 대응하지 않는다 —
  기존 HEAD 스탬프 캐시 패턴을 재사용한다(새로 발명하지 않는다).
- 실시간 갱신 공백은 재현 가능한 최소 사례로 먼저 확인한 뒤 고친다 — 추측으로
  고치지 않는다.

## Acceptance criteria

1. main 사본에 `Time:` 없음, 항해사 사본에 `Time: finished=...` 있음 → 화면은
   완료로 뜬다(현재는 안 뜸 — 이 버그를 고친다).
2. 그 반대(main에 있고 항해사에 없음)도 화면은 완료로 뜬다.
3. 두 사본 다 없으면 pending, 한쪽만 `startedAt`만 있으면 in_progress.
4. 사본 수·프로젝트 수가 늘어도, HEAD가 안 바뀐 사본은 매 요청 재스캔하지 않는다
   (캐시 히트를 실측으로 확인 — 예: git 호출 횟수 로그).
5. `gootte start`/`end` 실행 직후, 수동 새로고침 없이 화면이 반영된다(또는 이게
   기술적으로 불가능하다는 근거를 대고 대안 — 예: 짧은 폴링 주기 — 를 제안한다).
6. git이 완료/시작 판정에 관여하지 않음을 재확인(`grep`으로 `resolveTicketDone` 류가
   여전히 코드베이스에 없음을 확인 — 회귀 없음).
7. `pnpm -C code/web verify` green.
