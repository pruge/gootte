# 02 — check 목록도 issues 목록과 같은 자리에서 시작한다

**What to build:** 기능 카드 안에서 **`check` 아래 티켓 줄들이 `issues/` 아래 파일 줄들과 같은
왼쪽 끝에서 시작**하게 한다. 그 들여쓰기 값은 **한 곳에서만** 나오고, 두 목록이 같이 그것을 쓴다.

**Blocked by:** 없음 — 지금 착수 가능

**Status:** resolved (2026-08-09)

## 캡틴 지시 (2026-08-09)

> gootte에서 feature카드안에 check의 목록이 issues의 목록 시작 위치가 다르다. 맞춰줘.

## 무엇이 어긋났나 (사양 §실측 F16–F21)

트리의 문서 줄은 **깊이에 따라** 들여쓴다 — 깊이 0 은 1rem, 깊이 1 은 2.25rem. 그래서 `issues/`
안의 파일 줄은 **2.25rem** 에서 시작한다. 그런데 `check` 아래 티켓 줄은 그 식을 쓰지 않고
**1rem 고정**이다(F16). 1.25rem 이 어긋난다.

🟢 **머리글끼리는 이미 맞는다**(F17). `check` 와 `issues` 는 둘 다 깊이 0 의 형제라 같은 자리에서
시작한다. **어긋나는 것은 자식 줄뿐이다** — 머리글을 건드리지 마라.

🔴 **어느 값이 옳은지는 이미 코드가 말하고 있다.** 티켓이 하나도 없을 때 그 자리에 뜨는
"티켓이 없습니다." 는 **2.25rem** 에 있다(F18). 즉 **같은 목록이 비었을 때와 찼을 때 서로 다른
자리에서 시작한다.** 빈 문구 쪽이 issues 와 맞는 값이고, 티켓 줄 쪽이 물러나 있다.

🔴 **그리고 그 값은 두 번 적혀 있다**(F19) — 트리는 식으로 계산하고, 빈 문구는 그 결과를 손으로
적어 뒀으며, 둘을 잇는 것은 없다. 지금 맞아 보이는 것은 **우연**이다. 세 번째 손글씨를 더하면
다음에 또 어긋난다.

## 완료 시 시연 가능한 것

캡틴이 기능 카드를 열고 `issues/` 를 편다. **파일 줄과 그 아래 티켓 줄이 한 줄로 선다** —
눈이 위아래로 훑을 때 왼쪽 끝이 계단처럼 튀지 않는다. 티켓이 없는 기능을 열어도 빈 문구가
같은 자리에 있다.

## 완료 조건

### 자리

- **`check` 아래 티켓 줄은 `issues/` 아래 파일 줄과 같은 왼쪽 끝에서 시작한다.** 즉 깊이 1 이다.
- **빈 상태("티켓이 없습니다.")도 같은 자리다.** 지금 우연히 맞은 값이므로 그대로 두지 말고
  아래 §출처 규칙을 똑같이 적용한다.
- 🔴 **머리글은 손대지 않는다.** `check` 버튼과 `issues` 버튼은 이미 맞다(F17).
  맞는 것을 건드리면 무엇이 좋아졌는지 갈리지 않는다.

### 출처 — 이 티켓의 핵심

- 🔴 **깊이별 들여쓰기 값은 한 곳에서만 나온다.** 두 목록과 빈 문구가 **모두 그 하나**를 쓴다.
- 🔴 **손으로 적은 값을 남기지 마라.** 지금 두 곳에 따로 적힌 것(식 하나, 손글씨 하나)이
  이 티켓 뒤에는 하나여야 한다. 값을 옮겨 적어 맞추는 것은 이 티켓을 푼 것이 아니다 —
  **이번 어긋남이 정확히 그렇게 생겼다.**

### 제목 줄 맞춤

- **두 목록의 아이콘 칸 폭을 같게 해서 제목 글자도 나란히 선다.** 지금 문서 줄의 아이콘은 15px,
  티켓 줄의 상태 아이콘은 17px 라(F20) 줄 왼쪽을 맞춰도 글자가 2px 밀린다.
- 🔴 **트리의 나머지가 쓰는 값(15px)에 맞춘다.** 어긋난 쪽이 하나뿐일 때는 그쪽을 다수에 맞춘다.
- 🔴 **아이콘의 뜻과 색은 그대로다.** 크기만 맞춘다 — 상태 아이콘은 장식이 아니라 의미다.

### 잃지 않을 것

- 🔴 **`ticket-row-repair/03` 이 잡아 둔 고정 칸(단계 칸·완료일 칸)이 그대로 산다.**
  바뀌는 것은 줄의 **왼쪽 여백**뿐이고, 오른쪽 여백은 지금과 같다.
- 좁은 화면에서 줄이 접힐 때 **빈 줄이 생기거나 들여쓰기가 무너지지 않는다.**
- `pnpm verify` green.

## 테스트

**이 티켓이 들여쓰기를 처음 덮는다**(F21). 지금 트리 테스트는 *무엇이 뜨는지*와 *순서*만 본다.

| 상황 | 기대 |
|---|---|
| 🔴 `issues/` 를 펴고 티켓도 있는 카드 | 파일 줄과 티켓 줄의 **왼쪽 값이 같다** |
| 🔴 티켓이 없는 기능 | 빈 문구의 왼쪽 값도 **같다** |
| 🔴 값을 테스트에 직접 적었나 | **적지 않았다** — 공유 출처에서 읽어 비교한다 |
| 단계 칸·완료일 칸 | 기존 테스트가 **그대로 통과한다** |

🔴 **셋째 줄이 이 티켓의 안전망이다.** 테스트에 `2.25rem` 같은 숫자를 다시 적으면 손글씨가
**세 개**가 된다. 공유 출처에서 읽어 두 줄이 그것과 같은지 보면, 나중에 들여쓰기를 바꿔도
테스트가 거짓으로 깨지지 않고 **한쪽만 바뀔 때 깨진다** — 이 티켓이 막으려는 것이 바로 그것이다.

## 이 티켓이 하지 않는 것

- **들여쓰기 폭 자체를 새로 정하기.** 맞추는 일이지 고르는 일이 아니다. 두 목록이 갈라져 있을 때
  옳은 값은 이미 정해져 있다(F18).
- **줄을 표로 다시 짜서 모든 칸을 세로로 맞추기.** `ticket-row-repair` §열린 결정 Q1 이고
  캡틴이 아직 정하지 않았다.
- **트리의 순서나 기본 펼침 바꾸기.** `adr → issues → check → 낱장` 은 캡틴이 정한 것이다.
- **`check` 를 진짜 폴더처럼 보이게 하기.** 폴더가 아니라 화면이 만든 현황판이다(INV-1).
- **상태 아이콘의 뜻·색 바꾸기.** 크기만 맞춘다.
- **머리글 손대기.**

## 캡틴 확인

- **어디서** — gootte 대시보드에서 기능 카드를 하나 열고, 그 안의 `issues` 를 눌러 편다.
- **무엇을** — 파일 목록과 그 아래 티켓 목록의 **왼쪽 끝**을 위아래로 훑는다.
- **무엇이 보여야 하나** — 두 목록의 줄이 **한 줄로 서 있다.** 아이콘도, 그 옆 글자도 계단처럼
  튀지 않는다. 티켓이 없는 기능을 열면 "티켓이 없습니다." 도 같은 자리에 있다.

자리가 실제로 눈에 편해졌는지는 테스트가 판정할 수 없어 캡틴 눈이 필요하다.
