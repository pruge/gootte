# 03 — 지금 돌고 있는 기능이 위로 올라온다

**What to build:** 기능 목록의 정렬에 **단계를 하나 더 넣는다.** 처리중인 티켓을 가진 기능이
같은 무리 안에서 **먼저** 온다. 지금은 폴더명 순이라 돌고 있는 일이 목록 아무 데나 있다.

**Blocked by:** 없음 — 🟢 **지금 착수 가능**

**Status:** resolved (2026-08-10)

## 캡틴 지시 (2026-08-10, 원문)

> 정렬순서를 한단계 더 넣자. 처리중이 있는것을 2단계 로 먼저 부여주게해.

## 지금 정렬은 두 단계다 — 그리고 어디에도 안 적혀 있다

| 단계 | 무엇으로 | 어디 |
|---|---|---|
| 1 | 무리 — 남은 일 있음 → 티켓 없음 → 전부 완료 | `core/src/project/features.ts` §rank |
| 2 | 폴더명 |  같은 곳 |

🔴 **이 규칙은 사양 어디에도 적혀 있지 않다.** 근거가 코드 주석의 *"캡틴 피드백"* 한 줄뿐이라,
다음 사람이 무리 순서를 바꿔도 아무 문서가 반대하지 않는다.
**이 티켓은 단계를 더하면서 세 단계 전부를 문서에 남긴다.**

## 넣을 자리 — 1단계와 폴더명 사이

| 단계 | 무엇으로 |
|---|---|
| 1 | 무리(그대로) |
| **2** | **처리중인 티켓이 있는가 — 있는 쪽이 위** ← 새로 |
| 3 | 폴더명(밀려남) |

🟢 **"무리 위" 로 읽어도 결과가 같다는 것을 확인했다.** 처리중은 끝나거나 취소된 티켓에는 붙지
않으므로(`in-progress.ts` §markTicket), **처리중인 티켓을 가진 기능은 반드시 "남은 일 있음" 무리다.**
그래서 새 단계를 맨 위에 두든 무리 다음에 두든 순서가 달라지지 않는다 —
**무리를 건드리지 않는 쪽**을 고른다. 완료된 기능이 위로 튀어오를 여지를 아예 만들지 않는다.

## 🔴 이 티켓의 진짜 일 — 정렬이 처리중을 모른다

**지금 정렬은 처리중이 생기기 전에 끝난다.**

```
readFeatures()      → buildFeatures()  ← 여기서 정렬한다. 문서만 봤다. 처리중은 아직 없다
      ↓
applyInProgress()   ← 여기서 처리중이 얹힌다. 그런데 순서는 이미 굳었다
```

🔴 **그래서 정렬 함수 안에서 조건 하나 더 보는 것으로 끝나지 않는다.** 정렬하는 자리에는
그 사실이 없다. **정렬을 사실이 다 모인 뒤로 옮겨야 한다.**

🔴 **정렬하는 자리를 둘로 늘리지 마라.** 문서 정렬 한 번 + 처리중 정렬 한 번으로 나누면
두 비교 규칙이 갈라져 곧 어긋난다 — 이 저장소가 자매 기능에서 이미 한 번 고친 형태의 결함이다
(한 사실에 근원이 둘). **정렬은 한 곳에서 한 번만 일어나야 한다.**

🟢 **옮길 자리는 안전하다 — 색인으로 쟀다**(`codegraph impact "buildFeatures"`).
**제품 호출자는 `readFeatures` 하나뿐**이라 옮겨도 다른 화면이 순서를 잃지 않는다.

🔴 **다만 같이 움직여야 할 테스트가 셋 있다.** 색인이 이렇게 짚어 준다:

| 어디 | 왜 걸리나 |
|---|---|
| `core/src/project/features.test.ts` | **정렬된 결과를 `buildFeatures` 자리에서 확인**하고 있다 — 정렬이 옮겨가면 이 확인도 옮겨간다 |
| `core-io/src/features.test.ts` | 읽기 경로가 정렬을 거쳐 나온다고 본다 |
| `core-io/src/treehouse.test.ts` §`observe` | 관측 조립 경로가 같은 사슬을 탄다 |

🔴 **이 셋을 지우지 말고 옮겨라.** 정렬을 뒤로 미루면서 확인까지 같이 사라지면,
"처리중 없을 때 순서 그대로" 라는 안전선(아래 §테스트 네 번째 줄)이 근거를 잃는다.

**착수 직후 한 번 더 재라** — 이 표는 2026-08-10 색인 기준이고, 그 사이 PR 이 착지했을 수 있다.
🔴 고친 뒤에는 `codegraph affected` 로 **무슨 테스트를 돌려야 하는지** 확인하고 시작해라.

## 완료 시 시연 가능한 것

**캡틴**이 gootte 를 열고 프로젝트를 고른다 → **기능 목록 맨 위에 지금 돌고 있는 기능이 있다.**
처리중이 0 인 기능들은 그 아래에 예전처럼 폴더명 순으로 있다.

🟢 **캡틴은 오늘 이 화면에 바로 닿는다** — 목록 화면이 곧 첫 화면이다.

## 완료 조건

- **처리중이 있는 기능이 같은 무리 안에서 위로 온다.**
- **처리중이 둘 이상이어도 자기들끼리는 폴더명 순**이다 — 개수로 줄 세우지 않는다.
  🔴 개수로 세우면 사본 하나가 티켓 여럿을 건드릴 때 순서가 널뛴다.
- **무리 순서는 그대로다** — 다 끝난 기능이 위로 오는 일은 없다.
- **정렬하는 자리는 하나다.** 두 군데에서 비교하지 않는다.
- 🔴 **처리중 판정을 새로 만들지 마라.** 이미 계산된 값을 읽기만 한다(INV-1).
- **세 단계 전부를 사양에 적는다** — 이 티켓이 그 규칙의 첫 기록이다.

### 잃지 않을 것

- **무리의 뜻** — "티켓 없음" 이 완료로 접히지 않는 것, 완료가 맨 아래인 것.
- **남은 일 세기** — `countOpenFeatures` 와 맨 앞 무리의 크기가 같다는 관계.
- **프로젝트 목록** 쪽 세기는 이 티켓과 무관하다. 건드리지 마라.
- `pnpm run verify` green.

## 테스트

정렬은 순수 계산이라 **core 에서 덮는다** — 화면까지 올라갈 이유가 없다.

| 상황 | 기대 |
|---|---|
| 🔴 처리중 있는 기능 + 없는 기능, 폴더명은 없는 쪽이 앞 | **처리중 있는 쪽이 위** |
| 처리중 있는 기능 둘 | 자기들끼리 폴더명 순 |
| 🔴 다 끝난 기능 + 처리중 있는 기능 | 완료는 여전히 아래 — 무리가 이긴다 |
| 처리중이 하나도 없다 | **예전 순서 그대로** — 회귀 고정 |
| 티켓 없는 기능 | 여전히 가운데 무리 |

🔴 **네 번째 줄이 이 티켓의 안전선이다.** 처리중이 없을 때 순서가 바뀌면 정렬을 옮기다
무리 규칙을 흘린 것이다.

## 캡틴 확인

- **무엇을** — gootte 를 열고 jinwooauto 를 고른다.
- **무엇이 보여야 하나** — 지금 작업자가 붙어 있는 기능이 **맨 위**에 있다.
  🔴 위로 올라온 것이 실제로 눈에 먼저 들어오는지 봐 주시라 — 순서만 바뀌고 티가 안 나면
  머리글 쪽 강조를 따로 논의해야 한다.

## 이 티켓이 하지 않는 것

- **처리중을 더 잘 잡기.** 못 잡는 것이 있다는 것은 따로 확인됐고, 원인은 gootte 가 아니다
  — [`work-claims-its-ticket`](../../work-claims-its-ticket/spec.md) §넘기는 일 소관.
  🔴 **이 티켓은 잡힌 것만 가지고 줄을 세운다.**
- **머리글 색·강조 바꾸기.** 순서만 바꾼다.
- **티켓 줄의 순서.** 기능 안 티켓은 번호 순 그대로다.
- **프로젝트 목록의 순서.** 다른 화면이다.
