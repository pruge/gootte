# codegraph 쓰는 법 (gootte)

## 🔴 먼저 — 이 경고

> `No results found` 는 "코드에 없다" 가 아니다. 색인은 조용히 낡고, `codegraph status` 의
> "up to date" 는 신선도 근거가 못 된다. 없다고 판정하기 전에 ① `grep` 이나 파일 읽기로 교차확인하고
> ② 그래도 없으면 재색인한 뒤 다시 묻는다 ③ 그 다음에야 "없다" 고 말할 수 있다.

이 절이 맨 위인 이유: jinwooauto 의 격리 사본에서 이 순서를 건너뛰어 실재하는 심볼 둘
(`authorizeFsmGrant`, `grantedUserIds`)을 "없다" 고 사전에 기록한 사고가 있었다. 그동안
`codegraph status` 는 내내 "up to date" 라고 답했다 — 색인은 파일 단위가 아니라 **부분적으로**
낡을 수 있다는 뜻이다. 건너뛰면 **이미 있는 것을 없는 줄 알고 다시 구현하게 된다.**

또한 gootte 의 격리 작업 사본에는 `.codegraph/` 색인이 아예 없을 수 있다(jinwooauto 격리 사본
5개 중 4개가 그랬다). 사전을 채우거나 질의하기 전에 이 사본에 색인이 있는지 먼저 확인한다:

```
codegraph status code/web
```

색인이 없다고 나오면, 메인 작업 사본의 색인을 `-p`/경로 인자로 가리켜 질의하거나
이 사본에서 먼저 `codegraph init code/web` 로 색인을 만든다. 색인 없이 질의하면 전부 "없음" 으로
나오고, 그 결과를 사전에 적으면 이 사전이 **오판을 기록하는 장치**가 된다.

---

`.codegraph/` 색인은 **코드만 안다** — `import`·`function`·`interface`·`constant`·`type_alias` 같은
영문 심볼 노드뿐이라 **한국어로 물으면 걸린다는 보장이 없다.** 티켓의 한국어 개념어("실시간 저장소",
"프로젝트 발견")를 codegraph 가 아는 영문 심볼로 먼저 바꿔야 한다 — 그 변환표가
[`vocabulary/`](vocabulary/) 다.

사전은 이 저장소의 여섯 컨텍스트(`code/web/` 아래 워크스페이스)대로 쪼개져 있다: `contract.md`
`core.md` `core-io.md` `cli.md` `backend.md` `frontend.md`. 🔴 **어느 파일에 있을지 추측하지 마라** —
그걸 알면 이미 답을 아는 것이다. **찾을 때는 항상 `vocabulary/` 디렉토리 전체를 grep 한다.**

## 순서

1. 개념어로 사전 전체를 grep 한다. 걸리면 영문 앵커로 바로 질의:

   ```
   grep -rn "실시간" docs/agents/codegraph/vocabulary/
   ```

2. 없으면 `codegraph query "<짐작한 영문 이름>" -p code/web` 로 시도한다. **영문 식별자로
   질의해야 걸린다** — 자연어 한국어 질문은 앵커 추출이 불안정하다.
3. 결과가 나오면 `codegraph node "<심볼>" -p code/web` 로 소스+호출관계까지 확인한다.
4. `No results found` 면 **위 §먼저 의 3단계를 밟는다** — grep/Read 교차확인 → 재색인 → 재질의.
   교차확인 없이 "없다" 고 결론내지 마라.
5. 찾느라 헤맸다면 사전에 한 줄 남긴다 — 아래 §사전에 한 줄 남기기.
   교차확인·재색인으로도 못 찾은 이름은 **적지 마라** — 검증 안 된 추측은 사전을 오염시킨다.

## 사전에 한 줄 남기기 (크루)

**언제.** 한국어 개념어에서 코드를 찾느라 **헛짚었을 때만.** 헛짚었다는 것 자체가 그 대응이
비자명하다는 증거고, 다음 크루도 같은 데서 막힌다는 뜻이다. 한 번에 맞췄으면 적지 마라. 보통
작업당 0~2줄이다.

**무엇.** 심볼 이름과 **파일 경로만** 적는다. 🔴 **줄번호는 적지 마라** — 가장 빨리 썩는 값이고,
줄번호가 밀린 사전은 없는 것보다 나쁘다(§왜 줄번호를 안 적나 참고). 줄은 필요할 때
`grep -n "<앵커>" <경로>` 나 `codegraph node "<심볼>" -p code/web` 로 즉시 나온다.

**어떻게.**

1. `codegraph query "<앵커>" -p code/web` 로 결과가 나오는지 확인한다. 안 나오면 §먼저 의 3단계
   (grep/Read 교차확인 → 재색인 → 재질의)를 밟는다. 그래도 없으면 적지 않는다.
2. **경로가 파일을 정한다.** `code/web/backend/...` 면 `vocabulary/backend.md`,
   `code/web/contract/...` 면 `vocabulary/contract.md`. 해당 파일이 없으면 새로 만든다
   (첫 줄에 `# <컨텍스트> — 질의어` 와 그 컨텍스트의 코드 경로를 적고 같은 표 헤더를 쓴다).
   그 표 맨 아래에 한 줄 추가한다:

   ```
   | <한국어 개념어> | `<영문 앵커>` | <종류> | `<파일 경로>` | <YYYY-MM-DD> | <비고 또는 빈칸> |
   ```

   **한 심볼이 두 컨텍스트에 있으면** 형(type)을 소유한 쪽에 적고, 비고에서 다른 구현을 가리킨다.
   양쪽에 같은 줄을 복사하지 마라 — 둘이 따로 썩는다.

3. 🔴 **기능 커밋과 분리해 단독 커밋으로 만든다:**

   ```
   docs(codegraph): add "<개념어>" → <영문 앵커>
   ```

   기능 커밋에 섞지 마라. 섞으면 리뷰에서 묻히고, **그 PR 이 엎어질 때 검증된 지식까지 같이 사라진다.**
   단독 커밋이면 리뷰어가 그 한 줄만 따로 살릴 수 있다.

4. 그대로 자기 PR 에 실어 보낸다. 별도 절차 없다 — 머지되면 사전에 들어간 것이다.

**충돌.** 컨텍스트가 갈리면 대개 충돌하지 않는다. 같은 컨텍스트 파일에 두 브랜치가 동시에 추가해
충돌하면 해결은 항상 **둘 다 살리기**다 — 한쪽을 버리지 마라. 각 줄은 서로 독립적이다.

**같은 개념어가 이미 있으면.** 새 줄을 만들지 말고 기존 줄을 고친다. 심볼이 바뀐 경우라면
앵커·경로·확인일을 갱신하고, 커밋 메시지는 `docs(codegraph): update "<개념어>" → <새 앵커>` 로 한다.

### 왜 줄번호를 안 적나

jinwooauto 사전은 처음에 `경로:줄번호` 로 적었다가, **하루 만에 12줄 중 7줄의 줄번호가 틀어졌다**
— PR 몇 개가 착지하면서 위쪽에 줄이 추가됐을 뿐인데도 그렇다. 심볼 이름과 파일 경로는 같은 기간의
변경을 모두 견뎠다. 정밀도가 높을수록 빨리 썩고, 틀린 줄번호는 맞는 줄번호처럼 보여서 크루를
엉뚱한 곳으로 보낸다. **견디는 것만 적는다.**

## 명령 빠른 참고

색인은 `code/web/.codegraph/` 에 있다 — `query`/`explore`/`node` 는 `-p code/web` (또는
`code/web/` 안에서 실행), `status`/`init`/`index`/`sync` 는 위치 인자로 `code/web` 을 준다.

| 명령 | 용도 |
|---|---|
| `codegraph query "<영문 심볼/구문>" -p code/web` | 심볼 검색 — **결과 없음 ≠ 코드에 없음**(§먼저) |
| `codegraph node "<심볼>" -p code/web` | 그 심볼의 소스 + 호출자/피호출자. 현재 줄번호도 여기서 나온다 |
| `codegraph explore "<심볼 여러 개 또는 질문>" -p code/web` | 관련 심볼 소스 + 호출 경로를 한 번에 |
| `codegraph impact "<심볼>" -p code/web` | 이 심볼을 바꾸면 뭐가 영향받는지 |
| `codegraph index code/web` | **전체 재색인.** `No results found` 를 교차확인으로 뒤집었을 때 쓴다 |
| `codegraph sync code/web` | 변경분 갱신 — **자동 재빌드 훅 없음**, 세션 시작 시 직접 돌려라 |
| ~~`codegraph status code/web`~~ | ⚠️ **신선도 근거로 쓰지 마라.** 부분적으로 낡은 색인에도 "up to date" 라고 답할 수 있다(§먼저) |

## 왜 이렇게 만들었나 / 유지보수 기준

운영 계획·서식 기준·신선도 규율·이 사전이 만들어진 배경은 [`PLAN.md`](PLAN.md) 참고.
크루는 이 파일과 `vocabulary/` 만 보면 되고 `PLAN.md` 는 몰라도 된다.
